# SCARA kinematics: arm mode, homing boundaries and the RRF IK

Moved verbatim out of `../ARCHI.md` section 12.3 during the 4.4.0 documentation
compaction. ARCHI keeps the rules; the measured values and the reasoning live here.

- **The homed arm mode is machine state, not a preference** (since 1.12.0): `<HomePose armMode>` records the branch the machine actually rests in after homing (`1` on this Potterbot — `M114` measured joints `−18.489 / −116.054`, and a negative distal angle *is* mode 1). It flows to `RobotLimits.HomedArmMode` beside `CalibratedHomePose`, and **both** seed sites in `RobotChecks.Run` use it: the initial seed for a home-anchored program and the post-`G28` teleport reseed. The `elbow` input survives only where nothing anchors the walk (no `G28`, `RunPoints`, pre-home jog planning, the calibration fit) and now defaults to `1`. This matters because at the home pose both branches satisfy `A`/`B`, so `InverseRrf` never falls back — an elbow-seeded walk returned the mirror-image arm without any error, and `DuetJogComponent` latched that same wrong branch as the session's verified configuration
- **Two distinct homing boundaries - do not conflate them.** In an *unattended job file* the parser rejects per-axis `G28 X/Y/Z` for the SCARA (`GcodeParser.ParseHome`), because SCARA joint homing moves both Cartesian axes. Since 2.3.0 this rule is **routed through the machine profile**, not hard-coded: a Cartesian mechanism passes `allowPerAxisHome: true` (per-axis homing is ordinary practice there; the parse marks `HasPartialHome` and clears `HomePoseKnown`, since the post-home position is still unknowable offline — maintainer decision 2026-08-31). As an *attended operator action* the Jog component does offer per-axis `Hm X/Y`, behind two-press arming; homing there is verified (observed non-idle to Idle transition under a timeout, firmware reply inspection, per-axis `Homed` check) and fails closed if it cannot be confirmed
- **IK emulates RRF, not textbook SCARA** (since 1.9.0): `ScaraKinematics.InverseRrf` reproduces the firmware's arm-mode choice and `TryResolveTheta` its whole-turn wrap into the `M669 A` limits. `RobotChecks.Run`/`RunPoints` are one ordered stateful walk threading `(armMode, thetaTurns)` through every move, segment interior and arc sample, raising `ProblemKind.ConfigFlip` on a real discontinuity - arm-mode change always, theta wrap only on an exact integer turn-count disagreement, never on the atan2 branch cut. `InverseRrf` returns the reachable branch even when joints exceed A/B, so `CheckJoints` (not the IK) reports out-of-range and exploration mode keeps working
