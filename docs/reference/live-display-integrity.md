# Live display integrity and telemetry validation

Moved verbatim out of `../ARCHI.md` sections 8 and 15 during the 4.4.0 documentation
compaction. ARCHI keeps the summary and the rule names; the reasoning and the captures
that produced each rule live here.

## The five display-integrity invariants (ARCHI section 8)

**Display-integrity rules** (2026-09-09, after the third test round). Five invariants the live display now holds, each of which had a counter-example in a real capture:

1. **Telemetry is validated before it is posed, and a successful IK solve is not validation.** `Core/Duet/PoseEligibility.cs` decides `Show | Hold | Hide` from position validity, finiteness, halted/off, the unhomed rule and the machine's OWN per-axis envelope (`move.axes[].min/max`) with a 2 mm tolerance - `ScaraKinematics.InverseRrf` solves XY and assigns `j2 = z - BaseH`, so it happily solved the run `20260909-131323-d30110` approach replies that report Z at -389 mm with the same body declaring the Z envelope as 0-400. An axis with no usable limits is UNCONSTRAINED and the envelope reads UNKNOWN (the legacy `rr_status` path reports none); unknown bounds never refuse a pose. The bed plane is never treated as a universal Z=0 limit.
2. **Refusal holds, it never edits.** An ineligible observation keeps its raw coordinates for the recorder and the diagnostics window, is counted (`validity:` in `info`), holds the last VALID arm as a ghost with its reason, and invalidates `LivePoseTimeline` so nothing is interpolated across the boundary. The pose epoch is connection + configuration + arm + job + **retention run id**, so two prints of one file cannot share interpolation.
3. **Absence is drawn as absence.** Intended geometry is built from SEGMENTS (`Core/Robot/ToolpathRuns.cs`), each run carrying both endpoints, travel and print sharing the boundary point, and `MoveSampler.SampleWithBreaks` marking a break wherever a move's start does not coincide with the previous move's end - so an unresolved `G28` leaves a gap instead of a fabricated straight line. Display simplification is bounded-error (`Rdp`), never every-Nth-point, and reports its tolerance.
4. **Uncertainty withholds a line; it never asserts one, and never argues from the chord itself.** `TrailChordPolicy` withholds only when the acquisition gap exceeds `max(0.75 s, 2.5 * the measured cadence)`; requested speed plays no part, and `chord / elapsed` is never used as evidence about the route, because that is circular. A withheld line is a drawing GAP, attributed separately from a continuity break by `TrailBreakCounters`.
5. **Every rate is reported as the separate thing it is.** `LiveDisplayDetail` prints the configured interval, the effective target after the session clamp (named when it clamps), the measured acquisition interval, the coordinate round trip, the full poll elapsed time, the overlay interval and the publication age. Acquisitions are deduplicated by id because the glitch filter releases a held sample with its successor; parse/redraw counters are window deltas, not lifetime totals. Retention compacts older completed runs within 0.2 mm before it discards anything, and states what it did.

## Live viewport, telemetry acquisition and the axis glitch (ARCHI section 15)

- **The live viewport animates without solving** (2026-09-07, M3b): `LiveViewportController` (plugin) feeds `LivePoseTimeline` (Core) from `MachineSession.PollCompleted`, evaluates a delayed interpolation on a 60 fps `System.Threading.Timer` whose ticks only ask `LiveDisplayPolicy` for one coalesced UI callback, runs the SCARA IK with the observed branch on the UI thread, and publishes an immutable frame to `LiveRobotConduit` (a `DisplayConduit` drawing the shared base meshes under `RobotModel.PosedLinkTransforms`). Redraws go to Rhino viewports only; no `ExpireSolution`, no canvas invalidation. New epoch on connection generation, frame configuration, arm branch or job change; nothing is interpolated across one. `MachineSession.LastPollRoundTripMs` bounds sample age from request start. The observed trail (telemetry cadence, split at gaps) can be coloured by `LivePathDeviation` distance to the machine-frame G-code samples with a fixed Viridis legend; ambiguous correspondence is flagged, unavailable is grey. Since 2026-09-09 the viewport draws the robot, the bed, the intended path as thin context and the observed trail - no extrusion mesh, no nozzle marker, no on-screen timing text. **The arm is persistent** (same day, second capture): an unhomed or halted poll (the job's own G28, `cancel.g`) and an unsolvable observation hold the last posed frame instead of hiding it, a stale pose is drawn exactly like a fresh one (no ghost material), staleness starts at `max(3000, 6 x p95)` ms instead of `max(500, 2 x p95)`, the interpolation keeps a separate 1 s bridging bound, and `info` carries `arm pose held: ...` / `STALE` - the operator asked for no flashing and no colour change, so the indication is text, not appearance. Frames are compared by geometry only (the label left the frame), both publishers return "redraw owed" and `UiTick` issues **at most one Rhino redraw per tick** in its `finally`; the pump stops on a hidden pose and on a stale unchanged pose, a settled pose drops to a 500 ms staleness watch and then stops; the frame budget is 30 fps degrading to 15 and 10 with the existing hysteresis, and each shared base mesh is measured once instead of per frame. Observed geometry never consumes a smoothed frame. The intended path comes from `MachineSession.Jobs.Effective` through `Lugworm/Duet/ParsedJobCache.cs` (SHA-256 + frame key, four entries, LRU, one parse per key in flight on a thread-pool thread, the bytes copied inside the parse so a hit copies nothing); Live's `gcode` socket is a fallback used only when the session has no job, a mismatching wire is remarked, and an externally started job draws no path. `Core/Duet/LiveRenderStats.cs` carries the counters `info` prints: polls, round trip, observed interval, UI callback wait p95, frame build p50/p95, redraws vs callbacks, telemetry-triggered solves, parses and cache hits, trail points/segments, suspect and dropped samples, fps budget
- **A position is a validated observation, not a parsed number** (2026-09-09, `Core/Duet/ObjectModel.cs`, `Core/Duet/TelemetryAcquisition.cs`): a position axis requires a finite JSON *number*; a rejected X/Y/Z is absent from `Axes` and the snapshot reports `PositionValidity` (`Valid` / `Unreported` / `MissingAxis` / `NotNumeric` / `DuplicateAxis`) with a reason, so `JsonValue.Num`'s zero default can no longer fabricate a coordinate on the axis path. `AllHomed` is deliberately independent of position readability. Every snapshot carries an `AcquisitionStamp` - a process-monotonic id, the coordinate request's own start and receive timestamps (not the metadata completion), the connection generation and a composite flag for observations assembled from sequential or paginated requests - and `TakenUtc` is the coordinate response's arrival when a stamp exists. `MachineSession.Latest` is published monotonically by acquisition id, so a gated-command snapshot and a poll snapshot can no longer overwrite each other out of order
- **One continuity policy segments every observed toolpath** (2026-09-09, `Core/Duet/TrailContinuityPolicy.cs`): a new run or connection, an out-of-order acquisition, an invalid position, homing, a lost homed state, relative coordinate mode, a gap over 5 s, a backwards timestamp, a file-position or fraction rollback, a coordinate jump over 250 mm or an implied speed over requested x 4 + 20 mm/s (or 1000 mm/s) starts a new segment on the actual elapsed time; each observation is classified `Printing` / `Travel` / `StartupOrFooter` / `Paused` / `Jogged` / `Unknown`. The print-log recorder and the live viewport both consume it. Same-Z disagreement with the intended path over 5 mm (`Core/Duet/SameZPathIndex.cs`) is a **diagnostic trigger** that flags and preserves the raw sample - it never projects, deletes, smooths or breaks a segment, and `ConsecutivePathDisagreements` keeps a sustained fault visible. The seven operator-confirmed false positions of the 2026-09-09 dome capture are pinned as `SuspectPathDisagreement` by the replay fixtures under `Lugworm.Core.Tests/fixtures/dome-20260909/`; their source stage is **not** localized - a 3D nearest-point metric understates them and their implied speed is ordinary, which is why speed thresholds miss them
- **Raw telemetry is kept for diagnosis, bounded** (2026-09-09, `Core/Duet/RawTelemetryWindow.cs`): a 200-record ring of per-poll observations - the untouched response body capped at 4096 characters with its real length, endpoint, API mode, both request timestamps, acquisition/poll/connection ids, machine and user coordinates, homing flags, job identity and file position, speeds, arm configuration, parsed validity and the continuity verdict - raised by `DuetPollClient.RawBodyObserved` before parsing (coordinate request only). A suspect, invalid or discontinuous verdict, a transport failure, a reconnect or `MachineSession.NoteDiagnostic` captures the 200 polls before and 40 after, written as `diagnostics.jsonl` by the retention worker thread beside `print.csv` and mirrored and finalised the same way (`JobLogManifest` v2: `diagnosticsOffset`, `outcome`). `manifest.complete` describes the log; `outcome` describes the run - a halted print is never displayed as completed. Drops are counted separately (`LogRetentionService.DiagnosticsDropped`, a 5000-entry queue share) and a 4000-line session window keeps captures readable after the job log closes
- **The dome spikes are a firmware reply glitch, repaired from the reply's own second witness** (2026-09-09, second capture, `Core/Duet/AxisGlitchFilter.cs`): 1132 raw `rr_model?key=move.axes` bodies show that in about one poll in sixteen ONE of X/Y carries a `machinePosition` 15-53 mm off the contour while the other axis is exact and the same reply's `userPosition` for the bad axis sits on the contour (acquisition 412: X machine 199.144, X user 229.483, neighbours 224.7 / 234.4); the parsed value equals the body in every poll, round trip is 14 ms, and a SCARA cannot report one Cartesian axis right and the other wrong from one joint pair - so the stage is the firmware's object-model field, and polling faster only draws more of them. `MachineSession` runs every poll through the filter before the position consumers (retention, diagnostics, print log, `PollCompleted`); status facts and `Latest` see the poll at once. A reply in which exactly one axis disagrees with `userPosition` by more than 4 mm is held for one poll and repaired only when its machine value is off the midpoint of its neighbours and its own user value is on it; `userPosition` leads legitimately during long moves (it is the end of the current move), which is why the look-ahead exists. A repair is written on a filtered COPY of the snapshot (`PositionRepair`), becomes quality `MachinePositionGlitch` in the CSV with the raw value in the reason, is counted in Live's `info`, and never touches the raw body kept in `diagnostics.jsonl`; a disagreement nothing corroborates is left as reported and flagged. **Since 4.4.0 the filter never writes into the snapshot it is handed** (`ObjectModelSnapshot.WithPositionRepair`): each released `GlitchResolution` pairs the filtered `Snapshot` the position consumers use with the `RawSnapshot` exactly as polled and a `WasCorrected` flag between them, so a poll the session has already published keeps the coordinates the firmware sent and the raw and filtered readings stay comparable as evidence - the bracketing neighbour is still the filtered view, which is what the former in-place repair left behind, so every pinned decision including the dome replay is unchanged. The raw reply is paired with its snapshot at parse time (`RawProbe`) and the live timeline dates samples by their acquisition stamp

## The arm follows the intended path (2026-09-16)

**Why the model changed.** Runs `20260916-120054-49bee0` and `20260916-124703-99cbd9` (same job, SHA-256 `382ca39b…`) were polled at a steady 250 ms and still animated with jerk, most of all on travels, and the arm vanished briefly at every layer start. Four things in the raw `move.axes` bodies explain it, none of them a real excursion of the machine:

1. At the seam of every layer two consecutive readings put Y 8-16 mm off the contour while `userPosition` stood still (acquisitions 464/465, 549/550, 635/636 … one pair per layer). The 5 mm / 1.5 s persistence gate held them correctly, but it *invalidated the timeline* for each, so the arm was hidden at every seam.
2. Single readings with one axis 15-45 mm off along a straight run (480, 494, 511, 858) - the known one-axis glitch - that happen to land within 2-3 mm of a *later pass* of the same layer, so a nearest-point comparison against the whole job called them on-path.
3. The firmware reports the target of a queued move for one poll: the layer start 48 mm early (460, 786), the top of the Z hop into the next layer while the machine was still 36 mm short of it (540), a Z one layer high (462). A straight chord through such a reading is the spike the operator saw on travels.
4. A 12 s transport failure with reconnect during the approach (295 → 297); `Reconnecting` counted as disconnected and hid the arm.

**The rule now.** The arm presumes the machine executes its file (`Core/Duet/LivePathFollower.cs`):

- `LivePathDeviation` parametrizes its segments by arc length in file order (`PathPosition` on every query, `PointAt`, `Locate` over a progress window, `Continuous`). After the first fix a reading is located only inside `[progress - 100 mm, progress + max(200 mm/s, 2 × rate) × Δt + 25 mm]`; a candidate segment is clamped to the window, so a long segment that merely touches it cannot answer from outside. Progress never runs backwards inside the window: a reading projecting behind the fix holds it.
- A reading within 5 mm of the window's nearest point is progress; the arm is posed *on the path* there, and between two such samples `LivePoseTimeline` interpolates the progress and maps it back through the path, so the route between them is the file's own (anchored pairs bridge up to 3 s, measured pairs keep the 1 s bound). The display delay is two poll intervals plus 20 ms (100-800 ms) instead of one, which is exactly what makes one held reading invisible.
- An advance beyond `(2 × rate + 20 mm/s) × Δt + 5 mm` is *deferred*: the next reading corroborates it (it lies at or beyond it, minus 25 mm) and both are posed and drawn, the deferred one first at its own time, or it is dropped as a queued-move target or a glitch on a later pass. With the two-interval delay the deferral never reaches the screen.
- A reading more than 5 mm off is held (not posed, not drawn, kept in the logs) and the timeline is *not* invalidated. After 1.5 s of such readings the measured position is shown, animated from where the excursion began (the held readings are added then), and the trail starts a new run (`SustainedDeviation`). If the machine has instead reported itself elsewhere *on* the path for that long, the progress is relocated there and the arm jumps (new epoch), as it does after a fix older than 2.5 s.
- `Reconnecting` holds the last pose with `pose held: reconnecting` on `info`; only a closed or failed session hides the arm.

**What did not change.** The trail, the print log, `pos`/`J1`/`J3`/`J2` and every gate consume the observation, never the follower's decision or a frame; a held reading is counted on `info` (`arm:` line) and stays in `diagnostics.jsonl`. The fixtures under `Lugworm.Core.Tests/fixtures/seam-20260916/` replay both captures: the seam excursion (`seam.csv`) is held and the 48 mm early layer start deferred then corroborated; the layer-2 capture (`layer2-20260916.csv`, acquisitions 450-544) follows 88 readings on the path, defers two advances, holds five readings, never shows a deviation, never relocates, and every frame the display would have drawn lies on the intended path.

## Trail retention and pauses (5.0.0)

**The report.** On 2026-09-23 an operator paused a print twice, the second time for about 16 minutes, and on the third pause the Live View trail had lost everything before the first pause. The retention folder `20260923-081352-5c5de9` shows the recording was not the problem: one run id through all four pauses, `print.csv` 3,063 rows with no gap longer than the 32 s at job start, and the recorded positions within 0.27 mm (median), 0.89 mm (p95) of the G-code polyline in the machine frame over 10,483 points. The 135 points more than 5 mm off (1.3 %) were 134 one- or two-poll episodes of the known firmware artifacts (about 90 single-axis jumps of 15-45 mm, 25 queued-target reports, 9 seam Y offsets), evenly spread and not clustered at the pauses. No jagged edges.

**The cause.** The display's 5,000-point budget. The old rule compacted each completed run once at 0.2 mm and then discarded from the front; at 250 ms polls on curved walls the points are about 3.75 mm apart and 0.2 mm frees almost nothing. A replay of the 11,532 logged polls through that rule reproduced the report exactly: 2,673 points at pause 1, 4,612 at pause 2, and by pause 3 1,662 evicted, the earliest survivor 15 s before pause 1. Pausing never cleared anything; it only split runs.

**The rule since 5.0.0** (`Core/Duet/TrailRetention.cs`). Past the budget, stretches are simplified one ladder step at a time, lowest rung first and oldest first within a rung: 0.2, 0.3, 0.5, 1 and 3 mm. Simplifying simplified points adds the errors, so each stretch records its running bound (0.2, 0.5, 1, 2, 5 mm) and `info` reports the largest. The live run's newest 600 points stay at full detail; points leaving that tail catch up to the current rung. The planner hands out one step, the controller applies it and commits the removed count, and the planner is asked again, so no stale index is ever used. Points are discarded only past 4 x the budget. `TrailRetentionTests` pins a 25,000-point never-paused run keeping its first point and every observation staying within its stated bound.

**Pauses.** Only Processing and Simulating observations join the trail. The pause macro's lift and park (+34 mm Z in that print) and the move back were being drawn as part of the toolpath; they are still in the logs, which record observations regardless.
