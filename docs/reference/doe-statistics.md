# DoE statistics: inference, desirability, Pareto front and power

Moved verbatim out of `../ARCHI.md` section 16 during the 4.4.0 documentation
compaction. ARCHI keeps the pipeline and the component-facing rules; the statistical
definitions, the citations and the invariants live here. See also
`doe-calibration.md` in this folder.

- Interior front refinement follows crowding-distance thinning: bounded Nelder-Mead minimises max(lambda_i*(1-d_i)) + 0.001*sum(1-d_i), with normalised lambda_i = 1/max(d_i, 1e-9). The optimum and already refined extremes are skipped. A point is replaced only by a dominating result or a non-dominated result with greater overall D, then dominance runs again. Each search allows at most 200 iterations and 200 evaluations, preserving the maxFront*200 evaluation bound.

- Confirmation compares each measured response with its selected recipe's exact 95% prediction bounds, reporting inside/outside PI. This is a coverage check; unavailable intervals are not guessed. Measurements survive archive round-trips and clear when a different recipe is selected.

- Feasibility uses OLS on all 0/1 flags, with linear terms and interactions when the run count permits, never pure quadratics. This linear-probability mask needs no iterative solver and suits small data sets; predictions can exceed [0,1]. Candidates below `feasibleThreshold` (default 0.5) are masked before dominance. The report counts masked grid/sample candidates, excluding local refinement evaluations.

- Response transforms: `none`, `log1p`, `sqrt`, or Box-Cox with maximum-likelihood lambda on -2…2 in steps of 0.1 (including the Jacobian). ANOVA, R², PRESS and diagnostics use the transformed scale. Predictions use the inverse transform without a mean-bias correction; PI and CI bounds are inverted separately and are asymmetric. Box-Cox needs positive data, sqrt nonnegative data, and log1p values greater than -1.

For further reference on optimising in desirability space rather than raw response space, and on applying the weighting after the front, see Trautmann & Mehnen (2009), Engineering Optimization 41(1), 23–38, doi:10.1080/03052150802347926; Wagner & Trautmann (2010), IEEE Transactions on Evolutionary Computation 14(5), 688–701, doi:10.1109/TEVC.2010.2058119; Lu, Anderson-Cook & Robinson (2011), Technometrics 53(4), 353–365, doi:10.1198/TECH.2011.10087; Costa & Lourenço (2015), Transactions on Engineering Technologies, doi:10.1007/978-94-017-9804-4_27.

- `RsmInference` (2.3.0): prediction/confidence intervals, leverage + studentized residuals + Cook's distance per run, VIF per term - written from the OLS definitions (Cook 1977; Marquardt 1970), hand-derived test fixtures in `RsmInferenceTests`. RSM Evaluate appends a `diag` output and warns on Cook's D > 1 / VIF > 10; Desirability appends an `interval` output and marks alternatives whose predictions sit inside the recommendation's 95 % PI as **within-PI** - since 3.0.0 worded as a coverage check, not an equivalence test, awarded only when every response has an interval, and withheld with the gap reported otherwise (`DoeReportingTests`)
- `DesirabilityOptimizer`: Derringer–Suich weighted geometric mean, grid + Nelder–Mead, alternatives list, recipe sweep. The `alternatives` output lists local optima of the *scalarised* D - it is not a Pareto set and is labelled accordingly
- `ParetoFront` (2.3.0): non-dominated sorting + crowding-distance thinning (Deb et al. 2002, written from the definitions) over the vector of INDIVIDUAL response desirabilities - a `target=` goal has no monotone direction, so raw responses cannot be Pareto-ordered, and the d≤0 short-circuit deliberately does not apply while collecting (a d=0 point can be best-in-class on another objective; hiding those is the defect the front fixes). Off by default (`paretoOn`); the optimum is always inserted into the candidate set so "the D-optimum lies on the front" is a tested invariant, and thinning always preserves each objective's argmax. **Why desirability space and not response space:** the two jobs of a desirability function are separated here. `Goal.D(y)` is used as the per-response scaling that gives every goal kind a "bigger is better" direction (Trautmann & Weihs, SFB 475 TR 63/2004, who also prove the D-maximiser is Pareto-optimal for D > 0 - the invariant above); the weighted geometric mean, the *preference*, is not part of dominance and is applied after the front by the selector (Lu, Anderson-Cook & Robinson, Technometrics 2011, DMRCS). Invariants that follow: (a) the dominance relation is independent of every `w=`; (b) it is NOT independent of a goal's `Low`/`High`/`Target` - recipes outside a goal's acceptance window all score d = 0 on that axis and collapse into one representative (the higher DOverall), which is the preference-based Pareto reading of Trautmann & Mehnen 2009, not a raw-response front; (c) the shape `s=` is a strictly monotone reparametrisation of one axis (for d > 0), so dominance is invariant to it while crowding-distance thinning and the plot are not; (d) weights still touch the *sampled* front indirectly: the re-inserted D-optimum and D-alternatives, the near-duplicate representative and the thinning tiebreak all read DOverall, so a reweighted run may produce a slightly different row set even though no dominance decision changed; (e) since 2026-09-21 each objective's argmax is Nelder–Mead refined on that single dᵢ (never on D) and re-inserted when it improves, so the front's endpoints are local maxima of dᵢ rather than grid cells - skipped on a plateau (dᵢ = 1) or an infeasible objective (dᵢ = 0), and weight-independent by construction (`ParetoTests.Optimize_FrontEndpointsAreRefinedExtremes_NotGridCells`, hand-derived: a target at 0.3 on a grid of 5)
- `ParetoSelection` (3.0.0): the Pareto Select component's Core - `ParetoFrontSnapshot` validates the front tree (uniform arity, finite factors, d and D in [0, 1], unique bounded names; nothing dropped silently) and computes a canonical identity (SHA-256 over schema version, ordered names and canonically sorted invariant records, so branch order is not identity but every value, D and name is); `ParetoRecipe` stores a selection by value plus front hash and issues the `key` token; `ParetoSelection.Observe/Select/Reset` are the pure transitions (key wins over index, invalid requests never fall back, an unchanged index is not a standing order on a new front, a within-tolerance match on a changed front is a candidate needing acceptance, duplicates are ambiguous, tolerance `|a-b| ≤ 1e-9×max(1,|a|,|b|)`); `ParetoArchive` is the versioned, bounded JSON payload. Hand-derived A/B/C fixtures in `ParetoSelectionTests`. The selector never re-runs dominance or recomputes D; the report records that the front is sampled/thinned and may exceed `maxFront` by one. `ParetoFrontSnapshot.IndexOfWeightedBest` (2026-09-21) is the one deliberate exception to "never recompute": it applies a wired weight vector as the weighted geometric mean of the front's own d_i (zero d annihilates, zero weight drops the axis, refused with a reason on count/sign/all-zero, ties to the lowest row) and is labelled *response goals only* because factor priors are not on the front - it marks where a preference lands (the DMRCS *Combine* step) and never replaces the stored D. Not archived
- `PowerAnalysis` (2.3.0): Monte-Carlo power on the generated plan - simulate y = Xβ + ε, refit with the SHIPPED fitter (so aliasing on DSD/Taguchi is reflected honestly), count rejections per main effect. Simulation over noncentral-F on purpose: no noncentral distributions exist in MathNet and the estimate should mirror the analysis actually run (method as in skpr, Morgan-Wall & Khoury JSS 2021 - cited, not ported; skpr is GPL)
- Example measurements (2026-09-22): `docs/reference/example_doe_measurements.xlsx` is generated by `tools/gen_doe_example.py`, not typed - a ground-truth quadratic in coded units plus Gaussian noise per response, rounded to the precision the instrument would report. The rule the generator enforces is that noise must dominate the rounding step (sigma >= 3x) and that the centre replicates must differ: the hand-typed table it replaced had `print_time` as whole minutes with three identical centre points, so pure error was zero (lack-of-fit F infinite on an R2 = 0.993 model) and the +/-0.25 rounding residuals on the h = 0.75 face points gave Cook's D = 1.50 on runs 6 and 7 - an influence warning produced by the quantisation, not by an outlier. The generator refits with the same OLS the plugin uses and fails when any response exceeds Cook's D 0.45, lack-of-fit p < 0.15, R2 < 0.98 or predicted-R2 < 0.93 (`tests/tooling/test_doe_example_measurements.py`). Sigma is ~3x instrument repeatability, which lands R2 near 0.99 rather than 0.999 - a quadratic on a 15-run BBD has 5 residual df, so the honest evidence that it is not overfitted is predicted-R2 (PRESS, leave-one-out) staying within ~0.03 of R2, not R2 itself. The seed is searched and has to be: Cook's distance is scale invariant on this design (a 4000-draw MC puts P(max D > 1) at 27.5 % and P(max D > 4/n) at 90 % at 1x through 8x sigma, since a studentized residual does not depend on sigma), and a BBD face point has leverage 0.75 where D = 0.3*t^2, so |t| > 1.83 on any one run clears the threshold. An uneventful reference table is a chosen draw on any design this size, not a property a quieter instrument would buy
- Computed responses (2026-09-22): `RsmModel.IsComputed` marks a response whose values are calculated, not measured - a slicer time estimate is the case in hand. The model is fitted by the same OLS (so D and the front see it exactly like a measured response, and `log1p` remains the recommended transform for time), but `RsmInference` returns no prediction or confidence band for it, `ParetoPoint.PiHalf` is NaN on that axis, the within-PI marker and the confirmation check leave it out of their coverage sets, and the front tree and version-2 archive carry one 0/1 flag per objective so Pareto Select shows the prediction without ±. The flag is additive in the model JSON, the number tree and the archive; rows and models without it read as measured (`Computed_FlagRoundTripsJson`, `Computed_ResponseIsSkippedByWithinPiMarker`, `Computed_ResponseHasNaNPiHalf`)
- Augmentation (2026-09-22): `DoeDesign.AugmentFaceCentred` turns a 2^k or 2^(k−p) plan into a face-centred central composite design (Box & Wilson 1951, star on the faces so alpha = 1 and no run leaves the declared range). The star and centre block is appended, labelled `aug…` and shuffled on its own, so the block a lab has already printed keeps its order and labels; the fitter never proposes it, lack of fit is reported as before and the choice stays with the user (`augment = ccd-face`). With the star points the pure quadratics leave the intercept's alias set (`Fit_QuadraticEstimableAfterAugmentation`); `Augment_IsRefusedForDsdAndBbd` pins the refusal for designs that already carry three levels. This is not model-based sequential design: nothing proposes run n+1 from run n, which Appendix A of the external-repo memo still lists as absent
