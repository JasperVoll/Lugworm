# Component surface: GUID allocation, compatibility and per-component detail

Moved verbatim out of `../ARCHI.md` section 8 during the 4.4.0 documentation
compaction. ARCHI keeps the ribbon table, every socket and contract rule and each
component's identity; the allocation history and the per-component detail live here.

Since 5.0.0 (2026-09-22) the product, tab and category are **Lugworm** and component names
carry no prefix (`Slice`, not `IAMLab Slice`). GUIDs, nicknames and sockets did not change,
so this page's allocation table and every `.gh` document are unaffected.

## GUID scheme and allocation

**GUID scheme:** `<prefix>-00NN-4xxb-9c3d-aa00000000NN`, where `NN` is a decimal index and the third group carries the same index in hex, offset by `0xA0` (`0001`→`4a1b`, `0023`→`4b7b`, `0026`→`4bab`). Indices `0001`–`0033` are allocated with no gaps and no reuse (`0027`→`4bbb` is the 2.4.0 Graph Mapper, `0028`→`4bcb` the 2.6.0 Version (retired 2026-09-21, below), `0029`→`4bdb` the 2.6.0 Print Console, `0030`→`4beb` the 3.0.0 Pareto Select); Interlayer Time uses `0031`→`4bfb`, the 4.0.0 Legend `0032`→`4c0b` and the 4.0.0 Load Settings `0033`→`4c1b`; the next component takes `0034`→`4c2b`. Two allocations were corrected in 2.1.0: `RobotDefinitionComponent` and `RobotSimulationComponent` originally took `…0018-4abb-…` / `…0019-4abb-…`, reusing tails already held by `DuetTerminalComponent` and `DuetPrintJobComponent`. The GUIDs were distinct so nothing collided, but the `aa00000000NN` tail had stopped being a unique index. Both were still unreleased, so they were renumbered to `0025`/`0026` rather than left ambiguous. The two SCARA calibration GUIDs `a1a2c3d4-0020-4b4b-9c3d-aa0000000020` (`Calib Points`) and `a1a2c3d4-0021-4b5b-9c3d-aa0000000021` (`Scara Fit`) are retired exactly as the UR pair below is: the components were removed together with `Core/Calibration/CalibrationSequence.cs`, `ScaraFit.cs` and `CalibrationReport.cs`, their indices are never reused, and the contract gate is run with them passed to `tools/verify-rhino-contracts.ps1 -AllowedRemovals` (§21).

## Hidden compatibility components

**Hidden compatibility components** (`GH_Exposure.hidden`, still deserialized): `RobotComponent` (`Robot`, GUID `d1a2…0004`), superseded by **Robot Simulation** in 2.0.0; and since 3.0.0 `DuetConnectComponent` (`…0015`), `DuetStatusComponent` (`…0016`), `DuetJogComponent` (`…0017`), `DuetTerminalComponent` (`…0018`) and `DuetPrintJobComponent` (`…0019`), superseded by the **Duet Console** (`…0029`, Print Console in 2.6.0, Duet Console since 3.0.0, Machine Console from 4.0.0 to 4.4.0). The hidden five kept their `IAMLab Duet …` names through the 4.0.0 rename and dropped the product prefix with every other component on 2026-09-22 (`Duet Connect`, `Duet Jog`, …; only the contract key `name` changed) — they are the Duet-only components a saved document already names, and renaming them would change a shipped contract for no benefit. All five keep their GUIDs, sockets, gates and persistence byte-identical. They keep their GUIDs and behaviour so saved `.gh` documents open and solve unchanged; they are simply off the ribbon. The replacement deliberately took a **new** GUID (`a1a2…0026`) rather than inheriting `d1a2…0004` — its input list differs, and reusing a shipped GUID under a changed socket layout silently remaps saved wires. The 3.0.0 console is the deliberate exception and the reasoning is the mirror image: it **keeps** `…0029` because its identity did not change, and its outputs are strictly **append-only** (indices 0–7 unchanged, 8–19 new) so existing output wires survive. Only the removal of the `open` input shifts input indices, which is why `UPGRADE.md` tells operators to re-check the console's input wires once. The two former UR component GUIDs — `a1a2c3d4-0011-4abb-9c3d-aa0000000011` (`UR Robot`) and `a1a2c3d4-0012-4acb-9c3d-aa0000000012` (`UR Program`) — are retired in 4.0.0, not reassigned; their indices are never reused.

## Interlayer Time

**Interlayer Time** (`5 Analyze`, GUID `a1a2c3d4-0031-4bfb-9c3d-aa0000000031`): `Core/Analysis/InterlayerTime.cs` builds a sampled G-code or print-log timeline and matches each extrusion sample to earlier material below it using a spatial grid. `Core/Duet/PrintLogCsvReader.cs` reads recorded CSV; log file-position anchors or layer spans calibrate the estimated clock. `PlasmaColorScale` maps seconds to colours. The component reads files through `BackgroundFileWork`, converts paths at the document-unit boundary, and caches the analysis and layer-filtered line/vertex-coloured layer preview separately. Scrolling filters both the preview and the emitted per-layer trees out of those caches, so it never re-runs the analysis; the scale itself leaves the component as a `LegendSpec` wire rather than a viewport legend. See [Interlayer Time](../user-guide/interlayer-time.md) for inputs, outputs and sampling limits.

## Live View

**Live View** (`Duet Live` before the 4.0.0 rename; GUID `…0023` unchanged) shows the connected robot and its observed toolpath, and since 2026-09-09 nothing else: its inputs are `host, enable, gcode, bed, [limits: L1, L2, baseHeight, reachMax, reachMin, elbow], [robot: robot]` and its outputs `pos, J1, J3, J2, status, progress, info, trail`. The extrusion inputs (`extWidth`, `layerHeight`), the whole `log` feature group with its six inputs and the `layers` / `log` / `path` / `logInfo` outputs are gone - job logging lives on the Duet Console's always-on retention (§15), which never depended on Live View. `InputContractVersion` is 2 with eleven retired sockets (the three bed ones route to `LegacyBedMigration`; the other eight are named in one warning when they carried a wire or a literal), and because Grasshopper drops wires to removed outputs silently while index 7 is now `trail`, `Read` detects a pre-2 archive and remarks that those four wires must be deleted (`IamComponentBase.ContractKey` is internal for that). `trail` is a geometry tree with one branch per continuous drawn run of observed positions - never smoothed, never joined across a continuity break, never snapped to the intended path, with sparse chords withheld by `Core/Duet/TrailChordPolicy.cs` - which since 2026-09-09 withholds a line on the ACQUISITION GAP alone and never on requested speed times elapsed time (see the display-integrity rules below). Since 3.0.0 its viewport display is owned by `LiveViewportController` and drawn by a Rhino display conduit, and poll-driven re-solves are a **persisted context-menu preference** (`iamLiveAutoOutputs`): new instances default to viewport-only updates (outputs are a snapshot of the last solve); archives without the key keep automatic outputs, rate-limited to one re-solve per second through `MachineComponentBase.ExpireMinIntervalMs` (0 = unchanged behaviour for every other machine-control component); `MachineComponentBase.TelemetrySolves` counts the solves the telemetry subscription caused. Smoothing and the deviation overlay are persisted the same way.

## The Duet Console's output categories

**The Duet Console's outputs are append-only and, since 2026-09-09, categorised.** `IamComponentBase` gained output specs with a category and a pinned flag (`OutputSpec`, `OutputSpecs`, `OutputToggleGroups`, `OutputContractVersion`), an "Outputs shown" context-menu submenu, `iamActiveOutputGroups` persistence and an `iamOutputContract` migration that, once after a document loads and its recipients resolve, switches on every category with a wired socket; a connected output is never unregistered, by hand or by migration, and hiding a category with a wired socket is refused with a remark. The console's outputs fall into Connection (`host`, `connected`), Job (`status`, `state`, `progress`, `jobFile`, `uploaded`, `gcode`), Motion (`pos`, `homed`, `xHomed`, `yHomed`, `zHomed`, `bedOrigin`, `zZero`), Validation (`danger`, `problems`, `messages`), Overrides (`speedFactor`, `flowFactor`) and Logs / Diagnostics (`log`, `info`, `reply`); a new component shows exactly the three pinned outputs `host`, `status` and `gcode`. The Overrides category **keeps the persisted id `outTemperatures`** from when it also carried heaters, so a saved document's output-toggle state survives 4.1.0 - the display label changed, the contract string deliberately did not. Because indices move as categories toggle, the console emits by output NAME (`SetOut`/`SetOutList`) and never names an index. The historical layout below is what an old document carries: 3.0.0 grew indices 8–19; 4.0.0 appended **20–26** (the five heater/fan outputs plus `speedFactor` and `flowFactor`). **4.1.0 removed the five heater/fan outputs** with the rest of the thermals surface and kept the two override outputs, which are `M220`/`M221` readings rather than temperatures. That is a declared removal against the contract baseline (21), not an append - the only one in the console's history - and it is why `UPGRADE.md` tells operators to re-check a 4.0.0 document's console output wires. **`-1` still means "not reported"**, deliberately distinct from `0`: a transport that does not publish a factor and a factor genuinely set to zero must not read the same. Both participate in the expire policy's value equality exactly like `reply` does.

## Version (retired)

**Version** (`1 Slice`, 2.6.0 to 4.4.0, GUID `a1a2c3d4-0028-4bcb-9c3d-aa0000000028`) was removed on 2026-09-21, together with Core `SemVer.cs` / `UpdateCheck.cs` and their tests, the `BuildDateUtc` / `ReleaseManifestUrl` assembly metadata, the `IamReleaseManifestUrl` build property and the `-ReleaseManifestUrl` switch of `tools/release.ps1`. Its index is never reused, and the contract gate is run with the GUID in `-AllowedRemovals` like the UR and SCARA calibration pairs (§21). The installed version is read from Rhino's Package Manager or the `.gha` file properties; the per-component settings files still record it through `SettingsIo.InstalledVersion`, which reads the informational version the build stamps from the single csproj `<Version>` source.

## Background file work

**File-backed component work is asynchronous** (since 2.6.0, `Ui/BackgroundFileWork.cs`): G-code Save/Restart/pump-CSV, Overhang CSV, and RSM table read/report export capture immutable snapshots on the solver thread and run their file I/O in cancellable workers keyed by path + file identity (reads) or path + deterministic content hash (writes); one completion marshals through `RhinoApp.InvokeOnUiThread`, forces the completion solve through the heavy/manual gate, and disposes the request token source. Last good outputs replay while pending, an error is reported once and can be retried on the next explicit solve/trigger, rising-edge/write-on-change semantics are preserved, and workers detach on component removal/document close. A slow network share can no longer stall the canvas.
