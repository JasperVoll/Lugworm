# Print path logs, job identity and print history

Moved verbatim out of `../ARCHI.md` section 15 during the 4.4.0 documentation compaction.
ARCHI keeps the rules (read-only telemetry, one worker thread for all disk I/O,
exact-bytes job identity, archive-once history); the detail lives here.

- **The print path log is read-only telemetry** (since 1.10.0): the poll loop feeds each snapshot to Core's `PrintLogRecorder`, which emits records at layer start/end (firmware layer counter, Z-step fallback) plus every Nth poll, and streams them to CSV. A run is identified by the printing-state transition, not the file name - the first printing snapshot often carries no job fragment, and the legacy path nulls the name when `rr_fileinfo` fails. It sends nothing, passes no gate, and is wrapped so a file-I/O failure cannot escape into the poll loop's handler (which would invalidate the arm configuration and enter reconnect backoff). **All disk I/O runs on `PrintLogSink`'s own thread** - the poll loop only enqueues, because a blocking write has no timeout and would otherwise stall session keepalive and gate freshness when a log folder points at a dead network share. Because the poll runs at ~1 Hz, layer timestamps are accurate to ±1 poll and every boundary record carries its own `boundary_uncertainty_s` - it is not a hardware trigger. Motion telemetry (`RequestedSpeed`/`TopSpeed`/`SpeedFactorPercent`/`RawExtrusion`) is deliberately excluded from `ObjectModelDiff`: it changes on nearly every poll and would re-create the 1.7.0 canvas redraw storm
- **Every job is recorded, kept only on request** (2026-09-07): `Core/Duet/LogRetention.cs` is the retention state machine with an injected clock and file system (twelve deterministic tests); `Lugworm/Duet/LogRetentionService.cs` owns the disk adapter, the settings file and ONE worker thread with a bounded queue for every staging append and destination write - the poll loop only enqueues, exactly the `PrintLogSink` rule. `MachineSession` feeds it from an always-on recorder it owns and configures itself (the Live View `log` group this was once independent of was removed in 4.1.0), and mirrors its log lines as the job's events file. Staging is canonical until a destination copy is verified; destination length is the acknowledged offset (idempotent retry); finalisation verifies before deleting; corrupt manifests are quarantined; `RhinoApp.Closing` stops sessions, waits up to 3 s in total for them to finish disposing (their last records, the end row and the outcome, are enqueued as the poll loops unwind, and the service drops anything that arrives after shutdown) and then runs the clean shutdown. Details and states: `docs/reference/duet-control.md`
- **The print path log has a versioned schema** (2026-09-09): schema 2 appends `log_schema`, `run_id`, `segment_id`, `quality`, `classification`, `quality_reason`, `path_distance_mm`, `implied_speed_mms`, `acquisition_id`, `position_valid`, `position_invalid_reason` and `composite` after the schema-1 columns; an unusable position writes empty x/y/z with `position_valid=0`; `PrintLogCsvReader` reads both schemas
- **Job identity is exact bytes, not a filename** (2026-09-09, `Core/Duet/JobSnapshot.cs`): a `JobSnapshot` is the exact G-code bytes, their SHA-256, a parsed-path revision, the remote path, a `JobSource` and a per-run id (the same file printed twice gets two ids). `JobIdentityTracker` on `MachineSession.Jobs` keeps the **prepared** job apart from the **active** one, `Effective` is the active job while printing and the prepared one otherwise, and an externally started job is `External` with no bytes - its intended path is unavailable, never substituted by the Console's own input. `PrintConsoleState` projects `PreparedJob`, `ActiveJob`, `EffectiveJob` and `IntendedPathAvailable`
- **Every job is archived once, and Recent prints is a read of retention, not a second store** (2026-09-09): on a confirmed start from this session the exact bytes are written as `job.gcode` beside the log through the retention worker thread, staged and finalised like `print.csv`; `JobLogManifest` version 3 adds `gcodeSha256`, `gcodeBytes`, `gcodeOffset`, `runId`, `host`, `fingerprint`, `profileId`, `mechanism`, `transport` and `dryRun` (v1/v2 manifests list as not reprintable; a run with unknown bytes leaves no archive; a recovered archive whose length disagrees with its manifest is dropped). The Job page lists the last ten runs from the destination folder, so history survives a restart. Selecting a run prepares its snapshot (`JobSource.MachineFile`, the verified archive read back) and executes nothing; the active job stays bound to its own snapshot; "Print again" is the existing Validate -> verified Upload -> explicit Start flow on the verified bytes, refused on a hash or length mismatch, a missing or discarded archive, or a changed mechanism or transport, and warned on a changed host, fingerprint or profile; runs are identified by run id and hash, never by name; a history selection wins over a changed `gcode` input and says so. The actions ride on `ButtonSet.History` (`history:select:<id>`, `history:clear`) so the window never offers what the transaction refuses
