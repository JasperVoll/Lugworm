# Emergency stop and firmware reset recovery

Moved verbatim out of `../ARCHI.md` section 15 during the 4.4.0 documentation compaction.
ARCHI keeps the rule (`RecoveryState`, `ResetPolicy` paths A and B, bounded reset
transaction, observed-not-sent reporting, action epochs); the detail lives here.

- **E-Stop recovery is an explicit state, and its facts are separate** (2026-09-09, `Core/Duet/RecoveryState.cs`): stop requested, stop acknowledged (the endpoint answered), halt observed (a real Halted/Off status), transport unavailable with the transport's own reason, reset requested, reset delivery uncertain, recovery verified, homing required - plus the host, session and fingerprint the episode is bound to. A successful HTTP send is never a verified physical stop or a verified reset. It is immutable, projected through `PrintConsoleState` like the rest of the console state, and the session owns the authoritative copy because the recovery transaction re-derives its decision from it
- **Decision D4 gains a second, narrower path** (2026-09-09): `ResetPolicy` in `Core/Duet/RecoveryState.cs` is the one rule the footer button, the Terminal tab's `M999` and the session's recovery transaction all use. Path A is D4 unchanged (connected, Halted/Off, trusted, nothing pending). Path B permits a reset after THIS session's emergency stop when the machine's status can no longer be read - the 2026-09-09 lockout, where the reconnect after M112 left trust `Unknown` and every gated command refused - without the live trust probe but WITH the host / session / fingerprint binding recorded at stop time, and behind an explicit arm-then-send by the operator (`Recover (M999)` then `Press again`). An unrelated unreachable host is not a reset target, and the episode closes (D8) once the machine answers normally again on a newer connection generation, so one E-Stop never authorises blind resets for the rest of the session
- **The reset transaction is bounded and separate from the motion queue** (2026-09-09): `MachineSession.RunRecoveryResetAsync` waits at most 5 s for the command lock, runs its own prerequisite full object-model poll, re-decides against that fresh status, and afterwards discards the session state, invalidates the arm configuration and requires verified homing before motion. No job is ever resumed automatically
- **A firmware reset reports what was observed, not what was sent** (2026-09-09): `IMachineClient.ResetAsync` returns `ResetDelivery` - acknowledged, uncertain or a thrown refusal. The old catch-all `HttpRequestException` handler reported success for a delivery nobody had seen; the window now says "delivery UNCONFIRMED" and recovery is confirmed only by a later poll finding the machine live on a new connection generation with an acceptable identity. RRF's `SendAsync` carries the HTTP status on its `DuetException` so callers branch on the code, never on message text
- **An emergency stop cancels the command queue and opens a new action epoch** (2026-09-09): queued and in-flight gated commands are cancelled through a replaceable abort token, and `PrintConsoleReducer.ActionFinished` drops a completion whose epoch a newer action superseded - so an earlier action cannot dispatch after the stop or clear the newer action's pending state
