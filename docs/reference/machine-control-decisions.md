# Machine control: the decisions behind the gates

Moved verbatim out of `../ARCHI.md` section 15 during the 4.4.0 documentation
compaction. ARCHI keeps every gate and rule in short form; the reasoning, the defects
each rule answers and the implementation detail live here.

- **Arm configuration is tracked, and every hardware action is gated on it** (since 1.9.0): a verified full `G28` establishes `{armMode, thetaTurns}` by replaying the live `0:/sys/homeall.g`; while it is `Unknown`, configuration-sensitive actions are refused. Status transitions are attributed to a **specific submitted motion** - `MachineSession.MarkInitiatedMotion()` is called immediately before each accepted motion send and only there, never from the generic command wrappers. Outside an armed window only two transition shapes are accepted (leaving Idle, returning to Idle), so an external DWC jog, pause or cancel is recognised as foreign and invalidates - which matters because `cancel.g` homes and `pause.g` lifts the head. Raw expert Terminal commands are opaque motion and invalidate rather than authorise; emergency stop is deliberately unarmed so the transition to Halted invalidates
- **A refusal the operator cannot see is a bug** (since 1.12.0): a disabled capsule renders greyed with its reason in a **tooltip only**, so a connected-but-unhomed Print component looked broken — every button dead except E-STOP (which bypasses the gate by design), and no text anywhere. `MachineComponentBase.ReportActionGates()` now raises the active refusal as a runtime message. Severity is declared by the component that *produces* the reason, never matched out of its text: machine-state and safety refusals warn, connection/busy and input-dependent rejections remark, and routine prerequisites ("validate the job first", "select a file first") stay silent so an idle canvas is not permanently orange. Each component computes its reasons in one helper shared with `ButtonRows`, so a tooltip and its message cannot disagree. The message clears by itself — the machine-control components are not `Heavy`, so `Compute` re-runs on the `SessionChangeKind.Status` raised by `SetArmConfiguration`
- **Machine identity is probed and trusted explicitly** (since 2.6.0, AUD-SAF-004): every connection generation probes a fingerprint — `boards[0].uniqueId` on modern RRF, else a clearly labelled configuration hash over board type, kinematics, `config.g` and probed axis limits (it proves the configuration, not the physical board, and its display text says so). The Connect component persists the expected fingerprint in the `.gh`; the first user-initiated connection records the baseline, reconnects reprobe, and a mismatch or unprobed identity keeps the connection diagnostic-only — refused in the shared `ConnectedActionGate` (so every machine-control component shows the reason) AND re-checked inside the serialized command transaction, with only emergency stop and read-only diagnostics live. The transaction check re-derives any cached permissive trust state from the current expected/observed pair. "Trust connected machine" on the Connect context menu records the new identity behind an undo event. The design's M122 middle leg was deliberately not implemented: it would run through the shared gcode/reply drain at connect time and perturb reply correlation for queued commands
- **Transport is bounded end to end** (since 2.6.0, AUD-SAF-001/002/003): JSON/text responses stream under the request's linked timeout token with the 4 MiB cap enforced during the read; downloads put body reads and destination writes under the transfer timeout; teardown lock waits are bounded; `JsonLite` rejects non-finite numbers on every TFM (net7 parses `1e999` to Infinity where net48 fails the parse — both now refuse) and the object-model parser refuses non-finite axis data, so a malformed response can never satisfy a motion gate
- **The Duet Console is the single control surface** (since 3.0.0): `Duet Console` (GUID `…0029` — shipped as Print Console in 2.6.0, Duet Console in 3.0.0, Machine Console from 4.0.0, when a Moonraker transport made it machine-generic, and Duet Console again since 5.0.0, that transport having left in 4.1.0) absorbs connection, homing, jogging, origin capture, job control, terminal and go-to. It opens one external window per component (`Lugworm/Ui/Console/`) on the shared per-host session from `MachineSessionManager`. Core reduces the session change stream into an immutable `PrintConsoleState` (`Core/Duet/PrintConsoleState.cs`, tested); `Lugworm/Duet/PrintConsoleProjector.cs` projects it onto the window and the component outputs. Expire policy: the component expires only when an exposed output value changed, coalesced to one re-solve per 1000 ms, never while `live` is off — with the deliberate 3.0.0 change that `reply` is now output 10 and therefore participates in that equality. Every action runs the gates it always ran, through the same `Core/Duet/JobSafety.cs`, `JogPlanner`, `JobGate` and `Lugworm/Duet/DuetHoming.cs` inside `RunGatedCommandAsync`. **Decision D4: the console's Reset (M999) is stricter than the Jog capsule it replaces** — Halted/Off only, with no armed any-state override, and a console-entered `M999` in the Terminal tab takes the same predicate so the tab is not a bypass around the button. The accepted consequence is that recovering a wedged-but-not-halted board from the console needs E-STOP first (which halts) or the hidden Jog component. **Decision D5:** job validation runs synchronously at solve, cached by content hash, with Duet Print's policy key, and its verdict is held in the state as an immutable projection keyed by the gcode hash — cleared when the gcode or the policy changes, so `danger`/`problems`/`messages` can never describe gcode that is no longer wired in
- **Klipper machine control and the thermals surface were retired in 4.1.0.** `Core/Klipper/` (`MoonrakerClient`, `KlipperStatus`, its options), `RobotControlKind.Moonraker`, the `MachineCapabilities.Thermals`/`PressureAdvance` flags, `ThermalSnapshot`/`ThermalCommands`/`ThermalHistory`/`DuetThermals`, the console's Thermals tab and its `heat`/`fan`/`extrude`/`tune` gates all went with them. The reason is the one this document already gave as the sharpest weak point at 4.0.0: **Moonraker was never connected to a real printer**, and the lab prints LDM only, so the code could not be verified and served no machine. What survives is deliberate and narrow: `GcodeFlavor.Klipper`, `Core/Gcode/KlipperCommands.cs` and the fail-closed parser's acceptance of the three extended commands the generator emits (§11) - a Klipper board driving a ram extruder is still a supported *target*, it just receives its job as a file. The machine's speed and flow overrides survive too, as `Core/Machine/MachineOverrides.cs`: `M220`/`M221` are not thermals, and the console's `speedFactor`/`flowFactor` outputs keep working. The output category id stayed the literal string `outTemperatures` so saved documents keep their output-toggle state
- **The 4.0.0 rename moved no GUID and no socket** (f217f3c, a pure `git mv` plus identifier substitution): `DuetSession` → `MachineSession`, `DuetSessionManager` → `MachineSessionManager`, `DuetComponentBase` → `MachineComponentBase`, `DuetConsoleForm` → `MachineConsoleForm`; on the ribbon, **Duet Console → Machine Console** (`…0029`), **Duet Files → Machine Files** (`…0022`) and **Duet Live → Live View** (`…0023`). The namespace and the directory stay `Duet`, and `DuetPollClient` keeps its name because it *is* the Duet transport. The three renames change the contract key `name` only (the console additionally appends outputs); nicknames, GUIDs, sockets and persistence are untouched, which is why the contract gate needs `name` — not `all` — for Machine Files and Live View (§21). 5.0.0 reversed the console's half of it, `MachineConsoleForm` → `DuetConsoleForm` and **Machine Console → Duet Console** on the ribbon, because 4.1.0 had removed the Moonraker transport and only Duet boards are controlled directly; the GUID, nickname, sockets and the `duetprintconsole` settings key are untouched, and `MachineSession`, `MachineComponentBase` and Machine Files keep their names
- **Press-and-hold jogging holds one jog in flight, ever** (since 3.0.0): `Core/Duet/JogRepeatPolicy.cs` releases the next held step only after the previous gated transaction completed **and** a poll cycle that *started* after that completion has produced a snapshot. The transaction's own pre-send snapshot does not count (the poll loop and the command path fetch snapshots independently), and the planner's `notBeforeUtc` cannot serve either — it is a snapshot-freshness bound, not a pacing deadline. The acknowledgement is a monotonic poll **generation**, not a timestamp, because `ObjectModelSnapshot.TakenUtc` is stamped when parsing finishes. A `Busy` acknowledgement waits rather than terminating, since the planner gates on Idle and a long step is still executing when that poll lands; any refusal terminates the repeat instead of retrying into a closed gate; and an auto-repeat may never arm or consume the paused-jog maintenance override, which is armed as a side effect of the refusal itself
- **Latency:** `MachineSession.RequestPollSoon()` shortens the current cadence wait after an accepted command, through a dedicated wake semaphore that only the healthy-cadence wait observes — the loop treats a cancelled delay as shutdown, so sharing the session token would turn every "poll now" into a disconnect and strip the reconnect backoff. `PollCadencePolicy` raises the rate to 250 ms while any **owner-keyed** registered console window has focus and the machine is active, so two consoles on one host cannot blur each other's cadence off. Neither path adds a send, and the expire policy is untouched
- **The window explains a refusal in exactly two places** (2026-09-09): the tooltip of the disabled control and the component's runtime message. Since 2026-09-23 `ConsolePrimitives.Button` gives a disabled console button without a tooltip of its own the gate's reason for its id (`ButtonSet.Reasons`), so every refusal has its tooltip; the console does not call `ReportActionGates`, so a runtime message is not guaranteed for each one. The floating amber reason text that the Control, Terminal and Thermals pages drew below their buttons is gone together with `ConsolePrimitives.Refusal`, because it overlapped neighbouring content and, once neutered, left a blank strip; only the Dashboard keeps an inline reason for its single primary action, in the secondary text colour on a line whose height is reserved before the row is laid out. The Logs page shows session events through `Core/Duet/ConsoleEventGrouping.cs`: consecutive identical messages collapse into one line with a repeat count and a first-last time range (the dome startup repeated "arm configuration unknown" 21 times), classified by keyword into Connection / Job / Motion / Firmware / Errors tabs. Grouping is display-only - `LogTail`, the retention files and the `log` output keep every raw line
