# The bed definition and ControlKind enforcement

Moved verbatim out of `../ARCHI.md` section 12.1 during the 4.4.0 documentation
compaction. ARCHI keeps the wire formats and the rules; the separations, the removals
and the gate-path detail live here.

## The print bed definition

**The print bed is a second definition, on the same pattern** (since 2.1.0). `BedDefinition` / `BedDefinitionText` (`Core/Machine/BedDefinition.cs`) carry plate width, depth, centre and a default print centre as `iamlab-bed:v1:w=…;d=…;cx=…`, consumed by Place, Robot Simulation and Live View (§19). Two separations are deliberate and load-bearing:

- **Plate centre ≠ print centre.** `Center` is the plate; `PrintCenter` is where a part's bottom-centre lands — (468,−441) vs (339,−193) on this machine. `MoverComponent` therefore takes the definition's print centre only when a bed is *wired*; unwired it keeps its historical literal, because collapsing the two would relocate every part in every saved document.
- **Reach stays the robot's.** `ReachMinMm`/`ReachMaxMm` default to `NaN` = "ask the robot profile". The Print Bed component's `reach` override group was removed on 2026-09-08 — it was a second authority for the arm's reach that only Robot Simulation ever read and Live View ignored; the wire fields stay so an older `iamlab-bed:v1` text still parses, and no component produces them.

**One name on both ends of a definition wire** (2026-09-08): Print Bed emits `bed`, Robot Definition emits `robot` (its own input is `preset`), and every consumer's input carries the same name — the rule the `legend` wire already followed. Robot Simulation's outline output is `outline`, so `bed` on that component means the definition only. **Robot Simulation carries no second authority any more:** its `bed` group (`bedWidth`/`bedDepth`/`bedCenter`) and `robotopts` group (`baseOffset`, `armMode`) were removed the same day — the plate is the wired Print Bed's or the profile default, the SCARA arm mode is `RobotLimits.HomedArmMode` from `robot.xml` (the one authority §7 asks for), and Place is the component that moves geometry.

**One shared bed, with a shape** (2026-09-09): `BedDefinition` carries `BedShape` (`Rectangle`, `Ellipse` - equal axes are a circle) and owns the geometry every consumer draws through: `Contains`, `Outline`, `Bounds`, `SpanX`/`SpanY`, `GridLines` - pure millimetre maths in Core, converted to document units exactly once on the plugin side. A rectangle still writes `iamlab-bed:v1:…` byte-identically; an ellipse writes **v2** with `shape=`, because a 4.0.0 parser ignores unknown keys and would read an ellipse as a rectangle. Consumers hold **no** plate settings of their own: Live View and Robot Simulation draw nothing without a wired, valid bed (a remark says "connect Print Bed"; an invalid text is an error, still with no plate), and Place keeps `printCenter` because it is a per-part placement operation rather than bed configuration. Plate centre vs print centre and "reach stays the robot's" are unchanged.

## ControlKind enforcement and the transport choice

**`ControlKind` is enforced by the control components since 2.2.0.** Duet Jog, Duet Print and Live View carry an optional `robot` input (feature group, appended — no shipped socket moved). **Unwired means Potterbot SCARA and the pre-2.2.0 behaviour, bit-for-bit** — the mechanism parameter defaults to `Scara` all the way down (`JogPlanner.Plan`, `JobGate.Validate`), so saved documents change nothing. Wiring `generic-duet-cartesian` switches the gates to the Cartesian check path: `CartesianChecks` (envelope + Z + feed, arcs sampled; no IK, no reach annulus, no arm configuration, no mast) behind the same `StateGate`, step whitelist and feed caps. Unwired envelope inputs then defer to the firmware's own M208 report from the live snapshot, and jogging/validation refuse while any envelope axis is unknown — the Potterbot envelope literals are never inherited by a generic machine. The frame mirror (`MachineFrame`) is SCARA calibration, so the Cartesian path shows the machine's own coordinates. A profile that advertises no transport (`ControlKind.None` — `none`, `generic-cartesian`) fails closed: every planned action is blocked with the reason, only E-STOP/Reset stay live. **Since 4.0.0 `ControlKind` also picks the transport**, not just the gate path: it is the sole input to `MachineClientFactory.Create` (§15). `MachineSessionManager` still holds **one session per canonical host**. The rule that a lease asking for a different kind than the live session's closes that host first was never implemented: `MachineSessionManager.Acquire` has no kind check, and since 4.1.0 removed the Moonraker transport every session speaks Duet (`MachineSession.ControlKind` is fixed), so there is no second kind to close for. `EnsureFirmwareSafe` swaps the SCARA M669 contract for its Cartesian counterpart: M208 must be verified per axis, and a board whose `move.kinematics` parsed as SCARA refuses upload/start under a Cartesian profile. The gate tests are `CartesianDuetGateTests`; the SCARA default path is pinned by the pre-existing `JogPlannerTests`/`JobGateTests`.
