## Overview

Three independent pieces, all following the "definition on one wire" pattern 2.0.0
established for the robot: a bed that is described once instead of three times, a
visualization regression repaired, and a print-time estimate that finally knows the machine
has joints.

## 1. Print Bed - one plate, one definition

**New component** `IAMLab Print Bed` (**2 Place**, GUID `a1a2c3d4-0024-4b8b-…`). It emits
`iamlab-bed:v1:w=1000;d=700;cx=468;cy=-441;cz=0;px=339;py=-193;pz=0`, consumed by Place,
Robot Simulation and Duet Live.

Before this, the same plate was described independently in three files with nothing keeping
them in step:

| File | Carried | Default |
|---|---|---|
| `RobotSimulationComponent` | `bedWidth`/`bedDepth`/`bedCenter` | 1000×700 @ (468,−441,0) SCARA; 800×800 @ origin otherwise |
| `DuetLiveViewComponent` | `bedWidth`/`bedDepth`/`bedCenter` | 1000×700 @ (468,−441,0) |
| `MoverComponent` | `printCenter` | (339,−193,0) |

The first two agreed by coincidence, not by construction.

### Two separations kept deliberately

**Plate centre is not print centre.** `Center` is the plate; `PrintCenter` is where a part's
bottom-centre lands — (468,−441) against (339,−193) on this machine. They are different
quantities that merely live near each other. `MoverComponent` therefore uses the definition's
print centre **only when a bed is wired**; unwired it keeps its historical literal. Collapsing
the two would have silently relocated every part in every saved document.

**Reach belongs to the arm, not the plate.** `ReachMinMm`/`ReachMaxMm` default to `NaN`,
meaning "ask the robot profile". They exist so a physically restricted plate can narrow the
annulus — not so the bed becomes a second authority for the robot's reach.

### Compatibility

Every existing bed input survives and **overrides** the definition when wired, so saved graphs
are untouched. `BedPreview` was reused as-is; no geometry or drawing code was written.

**Duet Live takes plate geometry only.** Its `reachMin`/`reachMax` inputs feed the display IK,
so they were left alone; nothing on the Duet session, gate, poll or command path changed.

`BedDefinition` lives in `Core/Machine/`, is Rhino-free, and is versioned like the robot
definition so an unrecognised string fails loudly rather than resolving to wrong geometry.

## 2. Robot mesh visualization repaired

**Symptom**: the robot in Robot Simulation looked wrong compared to Duet Live — shimmering
surfaces and no silhouette.

**Cause**: unifying the two simulators in 2.0.0 kept the other simulator's draw call for both mechanisms:

```csharp
args.Display.DrawMeshShaded(mesh, RobotMaterial);   // lit DisplayMaterial
```

The SCARA components had always used the opposite technique on purpose. The shipped assemblies
carry coincident faces; under a lit material those z-fight and shimmer as the scrub slider
moves. Under monotone false colours the competing faces share a colour, so the artefact is
invisible, and form comes from a feature-edge overlay instead of from shading.

Restored in `RobotSimulationComponent`, for **both** mechanisms — z-fighting was never
SCARA-specific:

- `CreateMonotoneMesh(RobotColor)` + `DrawMeshFalseColors`
- a `_robotEdges` list, cleared per solve, drawn in `DrawViewportWires` at `RobotEdgeColor`
- crease threshold `FeatureAngleRad = 0.55` (~31°), matching the other two components

**The other simulator gained edges it never had.** Its mesh model had no edge method and
`RobotComponent` has no matching branch to copy, so there was nothing to port — that
component simply never drew them. Its `PosedFeatureEdges` is new, mirroring `RobotModel`'s
angle-keyed **base-mesh** cache
so edges are extracted once and only transformed per frame; recomputing `TopologyEdges` on every
posed duplicate is a per-tick hotspot on the ~100k-face assemblies. The extractor itself moved to
a shared `MeshFeatureEdges` helper so there is one definition rather than two.

The contract is now written down in ARCHI §12.2, because this is the second time it could have
been lost.

## 3. Robot-aware print time

`PrintStatsCalc` estimated time from Cartesian XY feed and acceleration only. For a SCARA that
is wrong exactly where it matters: near the reach boundary and near the dead zone, a modest
Cartesian feed demands joint speeds the machine cannot deliver, so the real print takes longer
than the estimate. `RobotLimits.MaxJointSpeed`/`MaxFeed` existed but print stats never read them.

**The model reuses the one `RobotChecks` already enforces** rather than inventing a second.
`Checks.cs` checks `joint_speed = (Δjoint / Δcartesian) - feed`; inverting it gives the
per-segment cap directly:

```
feed ≤ min(requested, MaxFeed, MaxJointSpeed - dist / |ΔJ1|, … / |ΔJ3|, … / |ΔJ2|)
```

Near a singularity a small Cartesian step demands a large Δjoint, the cap collapses, and the
segment correctly takes longer.

- `PrintStatsComponent` gains a `robot` input matching the established pattern. The component
  calls `RobotSimulation.Solve` for the joint samples, so `Core.Gcode` gains no solving
  dependency.
- `JointSpeedLimits` (`Core/Robot/JointSpeedLimit.cs`) carries the samples and ceilings.
- `PrintStatsResult` gains `JointLimitedTimeMin` and `JointLimitedSegments`, reported
  **alongside** the Cartesian numbers with a percentage delta, so the robot's cost is visible
  rather than silently folded into one changed number.
- `timeMin` publishes the most constrained model available: robot-limited, else accel, else the
  lower bound.

`robot = none` and non-kinematic profiles pass `null` and every existing path is bit-identical.

### Units wart, inherited on purpose

`MaxJointSpeed` is one scalar compared against °/s for the rotary joints and mm/s for the
prismatic one — exactly what `RobotChecks.Run` has always done. Reusing the shipped convention
beats silently redefining what the number means. Splitting it is a separate change with its own
migration.

## 4. Icon and tooling

`IamPrintBed.svg` in the existing style (24 px viewBox, `#28699f`/`#cde4ff`/`#12334f`, existing
gradient treatment): a plate in perspective with a grid and centre mark. Manifest count 24 → 25,
registered as `IamIcons.PrintBed()`.

**`make_icons.ps1` was broken and is fixed.** Edge writes progress and renderer warnings to
stderr; Windows PowerShell 5.1 wraps native stderr in an `ErrorRecord`, which the script's own
`$ErrorActionPreference = 'Stop'` promoted to a terminating error — so the run died on the first
icon even though the rasterize had succeeded. `$ErrorActionPreference` is now relaxed around the
native call only. Correctness is still judged by the exit code and `Assert-Png` (size, pixel
format, alpha coverage), which were never weakened. All 25 icons export and verify.

## 6. G-code preview height matched the output

**Reported**: at a 4 mm layer the G-code component's canvas preview showed the toolpath at
4 mm, but the executed job printed above it.

Two separate defects, both pre-existing — neither was introduced by 2.0.0 or 2.1.0 (the
`git diff` for `zoff`, `ZOffset`, `AppendPrintedMove` and the preview polylines is empty).

**a. The component double-counted the layer height.** `GcodeComponent` passed
`ZOffset = 4.0` while `GcodeConfig`'s own default is `0.0`. `ZOffset` is *nozzle-to-bed
calibration* — it is added on top of geometry the slicer has already placed at its true
height — so a 4 mm layer was emitted as `Z8.000`. Reproduced directly: preview Z = 4,
emitted `G1 … Z8.000`. The component default is now `0.0`, and the tooltip says plainly that
the slicer owns layer height.

**b. The preview never reflected `ZOffset` at all.** Every emitter writes `Z + zoff`, and
`StartPoint` is documented as "as commanded, incl. ZOffset" — but `PrintPolys`/`TravelPolys`
were collected at the raw geometry Z. So preview and output could not agree for *any*
non-zero offset, not just the default. The offset is now applied once where the result is
built, so no collection site can miss it, and the preview shows what the machine is
commanded to do.

Together: preview and output now agree at every offset, and with the corrected default both
sit at the true layer height.

> **Check your Z before the next print.** For a definition with `zOffset` left unwired this
> lowers the nozzle by 4 mm relative to previous behaviour — which is the point, but it is
> the direction that crashes if anyone had compensated for the old offset elsewhere (in the
> geometry, or in the machine's own Z zero). Wire `zOffset` explicitly to keep the old value.

## 7. Travel and deposition told apart by colour

Robot Simulation drew the whole path in one RoyalBlue line, so a travel jump looked exactly
like a printed bead. Deposition now stays RoyalBlue at width 2; travel is ochre
`(214,148,62)` at width 1 — thinner and warmer, so it reads as subordinate over the
near-white bed without competing with the reach rings.

Both sets come from `ExtrusionHistory`: the existing `VisibleRuns` for beads, and a new
`TravelRuns` returning their exact complement. Sharing that logic is what keeps a wire drawn
here and a bead built by `ExtrusionPreview` from disagreeing about which segments extrude.

**Travel now draws in both display modes.** Previously no wire was drawn at all while
`showExtrusion` was on. Travel is the one part of the path a bead mesh cannot represent, so
leaving it hidden there made every jump invisible. Deposition wires still give way to the
bead mesh as before.

## 8. GUID index scheme repaired

`RobotDefinitionComponent` and `RobotSimulationComponent` had taken `…0018-4abb-…aa0000000018`
and `…0019-4abb-…aa0000000019` — index tails already held by `DuetTerminalComponent`
(`…0018-4b2b-…`) and `DuetPrintJobComponent` (`…0019-4b3b-…`). The GUIDs were distinct so nothing
collided, but the `aa00000000NN` tail had stopped being a unique index, which is the whole point
of the scheme.

Both were still unreleased, so they were **renumbered rather than documented as a wart**:

| Component | Was | Now |
|---|---|---|
| `RobotDefinitionComponent` | `a1a2c3d4-0018-4abb-9c3d-aa0000000018` | `a1a2c3d4-0025-4b9b-9c3d-aa0000000025` |
| `RobotSimulationComponent` | `a1a2c3d4-0019-4abb-9c3d-aa0000000019` | `a1a2c3d4-0026-4bab-9c3d-aa0000000026` |

Indices `0001`–`0026` are now allocated with no gaps and no reuse. The third group is the index
in hex offset by `0xA0`, so the next component takes `0027`→`4bbb`.

**Safe because neither GUID ever shipped.** Both components are new in 2.0.0, which is itself
uncommitted; the repo's two saved `.gh` documents predate them and contain no reference. A
definition built against a pre-renumber local build would drop these two components on open —
if you have one, rewire them.
