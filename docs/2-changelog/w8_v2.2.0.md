# Changelog - Week 8, 31-08-2026, V. 2.2.0

**Release Date**: Week 8, 31-08-2026
**Version**: 2.2.0 (previously 2.1.0)
**Object**: feat: generic Duet control - profile-driven gates for Cartesian Duet machines

> **Note:** stacks on the uncommitted 2.0.0 / 2.1.0 working tree. If those are squashed
> before release, fold this entry in accordingly.

## Overview

2.0.0 made robot selection a definition on one wire but deliberately left the direct-control
components (7 Print) hard-wired to the Potterbot SCARA - "wiring the Duet components to the
definition is the natural next increment, and it needs its own gate tests first" (ARCHI
§12.1). This release is that increment: Duet Jog, Duet Print and Duet Live now accept the
robot definition, and a `generic-duet-cartesian` profile gets real, gated direct control of
any Cartesian Duet machine. The lab's Potterbot setup is untouched - an unwired `robot`
input is the SCARA path, bit-for-bit.

## 1. Core - the Cartesian gate path

- **`CartesianChecks`** (`Core/Robot/CartesianChecks.cs`, new): envelope-only validation
  for Cartesian machines. `RunPoints` checks each point against the M208 box
  ([XMin,XMax] × [YMin,YMax] × [ZMin,ZMax]); `Run` walks a parsed job - every endpoint,
  arc interiors sampled at `ArcChordTol` (an arc can bulge out of a box whose endpoints are
  legal; a straight segment cannot), per-move feed vs `MaxFeed` as a warning. No IK, no
  reach annulus, no arm configuration, no mast. Same start-pose policy as `RobotChecks.Run`:
  unanchored moves are validated at their endpoints only.
- **`RobotLimits.ZMin`** (new field, default 0): read only by the Cartesian path - a generic
  machine's M208 Z minimum may be non-zero. The SCARA validator keeps its long-standing
  hard-coded Z ≥ 0. Included in `ContentHash.LimitsKey`.
- **`JogPlanner.Plan`** and **`JobGate.Validate`** gain a `mechanism` parameter defaulting
  to `Scara` - every existing caller and cached hash is unchanged (mechanism is folded into
  the job-gate hash, so switching profiles re-validates). The Cartesian branch keeps the
  state gate, step whitelist and feed caps and swaps only the geometric check set.
- **Tests**: `CartesianDuetGateTests` (13) - Cartesian jog allowed where SCARA refuses
  (proving the arm checks are actually off), envelope/Z refusals, state-gate/feed/step
  refusals intact, per-axis `G28` still refused at parse for every mechanism, arc-interior
  envelope violation caught, overspeed warning + `blockWarnings`, mechanism in the gate
  hash, SCARA characterisation. 800/800 total, 0 warnings.

## 2. Components - the definition reaches the 7 Print tab

Duet Jog, Duet Print and Duet Live each gain an optional `robot` input in a new `robot`
feature group (appended - no shipped socket moves, saved documents unchanged):

- **Unwired = Potterbot SCARA**, the pre-2.2.0 behaviour exactly.
- **`generic-duet-cartesian`**: jog and job validation gate on the M208 envelope. Unwired
  limit inputs defer to the firmware's own M208 report from the live snapshot; while any
  envelope axis is unknown, jog/validate refuse with "machine envelope unknown" - the
  Potterbot's envelope literals are never inherited. Wired limit inputs still win. No
  arm-configuration requirement, no homeall.g machinery, no `y = -x` frame mirror -
  positions, trails and previews show the machine's own coordinates. Duet Live draws no
  arm and no reach annulus; the whole plate is printable.
- **`EnsureFirmwareSafe` (Duet Print)** swaps the SCARA M669 contract for a Cartesian one:
  per-axis M208 must be verified, and a board whose `move.kinematics` parsed as SCARA
  refuses upload/start under a Cartesian profile (the definition does not match the
  connected machine).
- **Profiles without Duet control** (`none`, `generic-cartesian`) fail closed: every
  planned action is blocked with the reason; E-STOP and Reset stay live.
- **Robot Definition**'s remark for non-SCARA Duet profiles now points at the three
  control components instead of saying direct control is Potterbot-only.

## Unchanged by design

- The SCARA gate path: `mechanism` defaults to `Scara` everywhere, `JogPlannerTests` /
  `JobGateTests` pin it, and no SCARA check, message or hash composition changed.
- `GcodeParser`: per-axis `G28 X`/`G28 Y` in an uploaded job remains refused for every
  mechanism (the Jog component's attended two-press `Hm X/Y` actions remain the only
  per-axis homing path).
- Calib Points and Scara Fit remain SCARA-only.
- All shipped `ComponentGuid`s, `THIRD-PARTY-NOTICES.md`, and every `PackageReference`.
