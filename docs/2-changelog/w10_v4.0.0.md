## Sections (filled per phase)

### 1. UR support retired

- Removed the two shipped UR components, IAMLab UR Program (`…0012`) and the
  hidden IAMLab UR Robot (`…0011`); both GUIDs are retired and their indices
  are never reused.
- Removed Core UR kinematics and safety checks (`UrKinematics`, `UrChecks`,
  `UrJobGate`) and the URScript output (`Gcode/UrScript.cs`).
- Removed the `ur5`/`ur10`/`ur10e` robot profiles from `RobotCatalog`; an
  `iamlab-robot:v1:ur10e` wire now fails with "unknown robot profile".
- IAMLab Robot Simulation lost its three UR-only inputs (`toolLen`,
  `radialYaw`, `yawDeg`); wires to its other inputs survive because
  Grasshopper reconnects by parameter name.
- Removed the embedded `UR_Robots.3dm` meshes and both UR icons.
- Removed UR from the README, INSTALL, UPGRADE (new 4.0.0 upgrade section),
  ARCHI.md, the wiki, the user guides, RELEASING.md, and the third-party
  notices (visose/Robots meshes, Hawkins IK); `docs/reference/UR_SUPPORT.md`
  and the UR Program wiki page were deleted.

### 2. Graph Mapper: tangent handles on Spline points

- Every Spline point carries an in and an out tangent handle (`GraphMap.H`, parallel to `P`;
  `NaN` = the automatic Fritsch–Carlson tangent). Hovering an anchor reveals its handles; a
  plain drag keeps the point smooth (both sides follow), Shift moves one side and makes a
  corner, Ctrl snaps the slope to quarters, double-click a handle returns the point to
  automatic. `Convert → Spline` points start automatic and gain handles the same way.
- Serialization stays byte-identical to 2.5.0 until a handle is set; then one trailing `h=`
  token carries the handles, so older files open unchanged and a corrupt handle list is
  dropped, never fatal. The per-family memory stores whole maps. Tests: `GraphMapTests`.

### 3. Interlayer Time: scrolled outputs, layer shading, legend wire, family icon

- The one `layer` input now cuts the emitted `perLayer`, `times`, `path` and `colors` trees to
  the layers it leaves visible, as well as the preview (D6). `report`, `layers` and `info` stay
  whole. The cut is a filter over the cached trees and `layer` is in neither the analysis key
  nor the draw key, so scrolling recomputes nothing.
- New `shade` input (display group): `none`, `alternate layers` (default) or `height ramp` tells
  adjacent layers apart when their times are similar. Bead meshes additionally get a fake
  overhead light on their own normals, because `DrawMeshFalseColors` is unlit. Shading is
  display-only — the `colors` output stays the unshaded Plasma colour, which is data.
- The in-viewport legend is gone: the `legend` input and its `DrawLegend` painter are replaced
  by a `legend` output (appended, index 7) carrying an `iamlab-legend:v1` wire for IAMLab
  Legend — the Plasma scale, `legendMax`, the "no bead below" grey and marks at whichever of
  `minTime` / `maxTime` are enabled.
- IAMLab Overhang appends the same kind of wire as output `legend` (index 4), and its three
  viewport colours are now read from `OverhangColors` in Core instead of being restated in the
  component, so the painted colours and the legend cannot drift apart. No other Overhang socket
  moved.
- New Core helpers `LayerShadeMode` / `LayerShading` (`Factor`, `Apply`, `FaceShade`) in
  `Analysis/InterlayerTime.cs`, and the Interlayer icon moves from the DoE pink family into the
  Core/fabrication blues.

### 4. IAMLab Legend

- New `5 Analyze` component (GUID `a1a2c3d4-0032-4c0b-9c3d-aa0000000032`): a legend for any data
  range - continuous ramp, thresholded classes, named groups or a size scale; named schemes
  (Plasma, Viridis, the four IAMLab family ramps, greys, traffic) or custom colours; font, text
  size and colour, decimals, tick count, frame; anchored to the viewport (eight anchors), fixed
  to a plane, or floating as a camera-facing billboard whose screen size stays constant;
  horizontal or vertical.
- Consumes the `iamlab-legend:v1` wire (`Core/Analysis/LegendSpec.cs`: versioned, escaped,
  culture-invariant, unknown keys ignored) that Overhang and Interlayer Time emit, and lets every
  explicit input override a field. Doubles as a colouriser (`colors` output) and emits a bakeable
  vertex-coloured mesh plus text planes for the model-space placements. Layout is one y-up frame
  (`Ui/LegendRenderer.cs`) shared by the 2D overlay and the two model-space backends.
- Core gains `Rgb`, `ColorSchemes`, `NiceTicks` (Heckbert) and `OverhangColors`; the component
  base gains `PType.Colour`; the icon uses all four family hues; `rasterize_svg.py` generalises the
  PIL icon rasterizer. Tests: `LegendSpecTests`.

### 5. Settings files and IAMLab Load Settings

- **Every IAMLab component can save and load its inputs.** Two new context-menu items,
  `Save settings…` and `Load settings…`, write and read one versioned JSON file
  (`*.iamset.json`) holding the values the component last solved with plus its active
  feature groups. The schema is Core (`IAMLabSlicer.Core/Settings/ComponentSettings.cs`),
  culture-invariant, with `"iamlab-settings": 1` and a stable `component` key; unknown
  versions and malformed values are refused with a message, unknown keys are ignored so
  an older build still reads a newer file's shared part.
- **Loading is one undoable step and never overwrites work.** An input with nothing
  wired gets a new slider / toggle / panel / value list carrying the file value (a
  slider's range is widened rather than the value clamped); an input wired to exactly
  one slider, toggle, panel or value list is set in place; anything else upstream — a
  component, an expression, several sources — is left alone and reported. The remark
  names the created / updated / skipped counts.
- **New component: IAMLab Load Settings** (`1 Slice`, GUID `a1a2c3d4-0033-…0033`,
  icon `IamSettings`). It points one document at a folder of settings files; from then
  on every `⇤ inputs` button builds its objects from the matching file and falls back to
  the built-in `ParamSpec` defaults where no file matches. `Apply to canvas` applies
  every match at once under one undo event.
- **Matching is by the `component` key inside each JSON, never by file name**, so files
  can be named after the material or the machine. Two files claiming one component are
  resolved deterministically (alphabetically first path wins) and both are reported;
  unreadable files and files naming a component this build does not have are listed on
  the `unmatched` output.
- **No watcher threads and nothing persisted.** `watch` (default true) re-reads the
  folder when a file's name, size or timestamp changed on the next solve; the
  registration lives in the session only (`Ui/SettingsRegistry.cs`) and is dropped when
  the component is removed or the document closes. One settings folder per document — a
  second Load Settings component is refused with an error rather than silently winning.
- Geometry, points, planes, colours and tree inputs are deliberately not captured; they
  are named in the save report. See [Settings files](../user-guide/settings-files.md).

### 6. Filament extrusion, temperatures, Klipper and Marlin dialects

- **Filament model** (`ExtrusionModel.Filament`, `Core/Extrusion/FilamentExtrusion.cs`): E is
  filament length from bead area ÷ filament area × flow; retraction is `RetractMm` of filament
  at `retractSpeed`; the header heats bed then hotend, homes, then waits (`M190`/`M109`,
  optional); first-layer temperature overrides are left behind at layer 2; the part fan runs
  from `fanFromLayer` (`M106`, boosted on a `minLayerTime`-slowed layer); the footer cools down
  and homes **X/Y only** (a full `G28` would drive Z into the print). The ram output is pinned
  byte-for-byte against the 3.0.0 text (`FilamentGcodeTests`).
- **Klipper dialect** (`GcodeFlavor.Klipper`): `SET_PRESSURE_ADVANCE` for advance, one
  `SET_VELOCITY_LIMIT ACCEL= SQUARE_CORNER_VELOCITY=` for M201/M205 (also re-issued softened
  around retraction travels), `SET_PRINT_STATS_INFO TOTAL_LAYER=` / `CURRENT_LAYER=` at every
  `; layer` marker, `M84` in the footer. `Core/Gcode/KlipperCommands.cs` is the one place that
  recognises extended commands: the fail-closed job parser accepts exactly those three (user
  macros stay refused like M98), the terminal classifies `STATUS`/`HELP`/`QUERY_ENDSTOPS`/
  `GET_POSITION` as diagnostic and a fixed set as advanced, `FIRMWARE_RESTART`/`RESTART` take
  the M999 Halted/Off rule, and the restart planner keeps the two modal settings and **re-heats
  and waits before any motion** on a thermoplastic job.
- **Profiles**: `RobotProfile` gains `Process` (Paste / Thermoplastic) and `DefaultFlavor`;
  `RobotControlKind.Moonraker`; new profiles `generic-klipper`, `generic-klipper-fdm`,
  `generic-marlin-fdm` (aliases `klipper`, `moonraker`, `klipper fdm`, `marlin`). Every
  pre-4.0.0 profile keeps Paste + Duet RRF, so unwired generator output is unchanged.
- **G-code Generator**: `firmware` value list gains Klipper and, unwired, follows the profile's
  default; new `fdm` group (extrusion model dropdown, filament diameter, flow, retraction,
  temperatures, wait, fan, boost, cooldown - a thermoplastic profile selects the filament model
  with sensible defaults even while the group is off); `filamentMm` output appended (index 10);
  `info` reports the model. **Robot Definition** appends `process` and `flavor` outputs.

### 7. Machine transport seam, Moonraker client, Machine Console with Thermals

- **Renames, no GUID moved** (f217f3c): `DuetSession` → `MachineSession`, `DuetSessionManager` →
  `MachineSessionManager`, `DuetComponentBase` → `MachineComponentBase`, `DuetConsoleForm` →
  `MachineConsoleForm`; the components are now **IAMLab Machine Console** (`…0029`), **IAMLab
  Machine Files** and **IAMLab Live View**. The five hidden 3.0.0 Duet components keep their names.
- **The transport seam** (262b183): `Core/Machine/IMachineClient.cs` is exactly the member set the
  session, the components and the gates called on the Duet client, plus `MachineCapabilities`
  (simulate, home macros, thermals, maintenance reset, motion-baseline source) so the session and
  the window hide what a machine would refuse instead of offering it. `MachineClientFactory.Create`
  picks the client by `RobotControlKind`; `MachineSessionManager` keys a host by kind and closes a
  host that changes kind. `DuetPollClient` implements the seam unchanged; the Duet path stayed
  byte-identical through the extraction (every 3.0.0 test green, no fake touched).
- **MoonrakerClient** (a684d2d, `Core/Klipper/`): Klipper through Moonraker's HTTP API, polling
  only (P3, no websocket), `X-Api-Key` from the console's `password` input. `server/info` and
  `printer/info` identify the board, `printer/objects/query?configfile=settings` is hashed for the
  identity fingerprint and read for the motion baseline (`printer.cfg` limits), one objects query
  per poll (`webhooks`, `toolhead`, `gcode_move`, `print_stats`, `virtual_sdcard`, `idle_timeout`,
  `extruder`, `heater_bed`, `fan`, every heater/sensor/fan discovered at connect), `gcode_store`
  drained for replies, `printer/gcode/script` for commands, `server/files/upload` with a SHA-256
  checksum the server verifies, list/metadata/download/move/delete under `gcodes`, `print/start|
  pause|resume|cancel`, `emergency_stop` and `firmware_restart` (Halted only). `KlipperStatus`
  maps `klippy`/`print_stats`/`idle_timeout` to the console's machine states (Starting, Halted,
  Off, Processing, Paused, Busy, Idle) and lazily re-probes when Klippy comes up.
  **Kinematics fail closed** (P6): only the Cartesian families are accepted; a delta, polar or
  unknown kinematics sets `KinematicsRefusal` and refuses upload/start under every profile.
  HTTP 401/403/422 and JSON `error` bodies surface as `DuetException` like an RRF refusal.
  33 tests against a fake Moonraker handler.
- **Thermals** (c76817d): `ThermalSnapshot` (heaters with kind/target/power, fans, the firmware's
  own `can_extrude` verdict, speed/flow factor, pressure advance) rides on every snapshot.
  `DuetThermals` parses RRF 3 `heat`/`sensors.analog`/`fans`/`tools` into firmware-slot names
  (`extruder:N` through the tool table, `bed:N`, `chamber:N`, read-only `sensor:N`; a multi-heater
  tool stays read-only). RRF reports no cold-extrusion verdict, so manual extrusion is
  Moonraker-only. `ThermalCommands` builds the commands per transport (M568/M140/M141/M106 on RRF;
  `SET_HEATER_TEMPERATURE`, `SET_FAN_SPEED`, `M106`, `SAVE_GCODE_STATE`+`M83`+`G1 E`+
  `RESTORE_GCODE_STATE` on Klipper; M220/M221; `SET_PRESSURE_ADVANCE`), range-checked, identifiers
  validated, never a heater wait. `ThermalHistory` keeps a bounded 10-minute ring per heater
  (2400 samples, 4 Hz cap), seeded from Moonraker's `temperature_store` through the seam's
  `GetThermalHistoryAsync` (null on RRF) and merged on reconnect without overwriting live samples.
  **Duet poll cadence:** heaters and fans every poll only on a machine with settable heaters; tool
  map and extra sensors every tenth poll; a heaterless (paste) machine reads all four keys every
  tenth poll and carries the last snapshot between - the Potterbot's poll cost barely moves.
- **Console state and window:** `PrintConsoleState` gains `Thermals`, `ThermalHistory`, `Process`,
  `Transport`, `CanSimulate`, `ThermalsSupported`; `ButtonSet` gains `heat`/`fan`/`extrude`/`tune`
  with reasons (connected, trusted, snapshot ≤ 3 s old, machine live and not halted/off; extrude
  also idle without a job and `can_extrude`). `ConsoleNextAction` offers **Heat up** (Thermals tab)
  before Start on a cold thermoplastic hotend. History-only ticks never change the outputs. The
  window gains a **Thermals** tab (index 5; shown when the profile is thermoplastic or the machine
  reports heaters): paged heater table (target, −5/+5, Off), presets (PLA 210/60/100, PETG
  235/80/50, ABS 250/100/0, Off; editable, console settings v2), all heaters off, temperature chart
  (dashed targets), fans (0/25/50/75/100 % and a slider), manual extrude/retract (1/5/10/50 mm at
  1/2/5 mm/s), speed/flow/pressure-advance with a second press to confirm; the Dashboard shows a
  heaters strip. Six console icons added.
- **Component:** the console takes its transport from the wired robot profile (`Duet` or
  `Moonraker`; `host[:port]`, `password` = API key on Moonraker); `dryRun` is ignored with a remark
  on Moonraker; `thermal:*` action ids run through the same gated command path (`StateGate`, live
  state re-checked on the fresh snapshot, `MarkInitiatedMotion` for E moves). **Outputs 20–26
  appended:** `hotend`, `hotendTarget`, `bed`, `bedTarget`, `fan`, `speedFactor`, `flowFactor`
  (−1 = not reported), rounded to whole degrees and whole percent so a resting hotend's tenth-of-a-degree
  wander never re-solves the canvas. Machine Files and Live View accept either kind.
- Tests: `MoonrakerClientTests` (33), `DuetThermalTests` (+cadence), `ThermalCommandsTests`,
  `ThermalConsoleTests`, `ThermalHistoryTests`; console parity checks for the thermal transaction
  and the conditional page. Suite: 1348 Core, 358 × 3 smoke, 25 tooling.

### 9. Review pass (2026-09-08): bugs, safety gaps, dead code

Three read-only reviews of the 4.0.0 diff plus a Roslyn dead-code pass (IDE0051/52/59/60 and an
unreferenced-member scan). Everything below is fixed and covered by the suites (1351 Core,
360 × 3 smoke, 25 tooling, zero warnings).

- **Bugs:** the Machine Console never applied its `pollMs` input to the session (inert since
  3.0.0); Disconnect passed the composite `host|kind` rebind key to `CloseHost`, which could no
  longer match a session (regression of this branch); the console settings-file warning was
  recorded and never shown (now on the retention status's attention line); a Legend title or unit
  ending in `:` corrupted the wire (first-field test made explicit; `scheme` unescaped
  symmetrically; NaN marks filtered); the Klipper header emitted `M204` and then overwrote it
  with `SET_VELOCITY_LIMIT ACCEL=` (print accel now folded into the one ceiling, `M204` not
  emitted on Klipper) and capped ACCEL at the Z limit (Z keeps `max_z_accel`, noted, not folded);
  `filamentMm` counted primes but not retractions (now the net E); the settings integer guard let
  2^63 wrap to `long.MinValue`; a `heater_generic` classifier with identical branches; the `fan`
  output took the first fan even when thermostatic (first settable fan now); preset apply
  resolved by grid row while blank-named rows were dropped on save (blank names refused, apply
  resolves by name); the thermal dialogs accepted values the send would refuse (bounds now per
  heater kind and per key).
- **Safety:** the hidden Jog's armed reset override reached Klipper's `FIRMWARE_RESTART`
  (aborting a print); the session now honours it only when the transport's capability allows.
  Moonraker's move-overwrite guard failed open on any error (only a definite 404 proves the
  destination free); download/verify/size paths now refuse a path outside the gcodes root; a
  timeout or unreachable host on emergency stop, download and body reads now surfaces as the
  same `DuetException` the reconnect and Klippy-down paths filter on (`DuetException.StatusCode`
  carries the HTTP code instead of message matching); the poll loop and a command shared the
  gcode_store cursor unsynchronised (one drain lock, replies handed to the collecting command);
  the Duet thermal cadence state is read into locals and written under a lock (the poll loop
  and gated commands snapshot concurrently); the kinematics refusal is checked under every
  profile, not only the Cartesian branch; the extrude transaction re-checks "no job loaded" like
  its button; cooldown and preset apply address every device they can and report the rest
  instead of aborting on one unnamable heater; legacy components adopt the host's transport
  instead of replacing a Moonraker session with a Duet client; the preset editor's Apply follows
  the heat gate; the form reads the latest state once under its gate.
- **Dead code removed:** about 45 members and parameters across Core and the plugin (see the
  commit messages); `ThermalsSupported` and three unread state projections replaced by
  `PressureAdvanceSupported` from `MachineCapabilities.PressureAdvance`; the Thermals tab id
  lives in one constant; the projector no longer builds an output snapshot per poll while
  `live` is off; the plane-placed Legend keeps its texts instead of rebuilding the mesh per
  frame; Load Settings skips files over 1 MB and no longer caches an empty key set after a
  partial type load; GraphMap reads never mutate the handle array.
- **Robot Simulation report (2026-09-08):** an `ArgumentException` in Core followed by a Rhino
  crash when a simple G-code was connected. Not reproducible from the parse/simulate path (tested
  with hand-written, slicer-style and Generator-made G-code for none/Cartesian/Potterbot); the one
  reachable site is the profile resolver when text lands on the `robot` socket, which echoed the
  whole input. Fixed: bounded resolver messages, the whole `Compute` behind one catch (the
  simulation, bead, bed and arm ran unguarded), and the parser accepts slicer status lines
  (`M105`, `M73`, `M110`, `M113`, `M118`, `M119`, `M155`, `M2`) and the free-text `M117`/`M118`
  payload. `M30` stays refused.

### 13. E-Stop recovery state and Reset policy (2026-09-09)

Section 1 of `docs/dev/OBSERVED-ISSUES-PLAN_2026-09-09.md`. On 2026-09-09 the operator
pressed E-STOP on the Machine Console during the dome print. The robot stopped, the job
events log recorded `M112` at 09:55:05.165, the firmware reported cancellation and the run
ended `Halted` - and afterwards **Reset could not be pressed at all**, with Duet Web Control
unable to reconnect either. There is no `M999` entry in the log because none was ever
attempted. Reset required connected + Halted/Off + trusted + no pending action + a fresh
snapshot, and the emergency stop had just taken away all of them at once: the transport was
gone, the reconnect had reset machine trust to Unknown, and the pending E-STOP action was
still standing. Every individual gate was defensible; together they locked the operator out
of the one control that recovery needs.

**What changed**

- **`IAMLabSlicer.Core/Duet/RecoveryState.cs` (new)**: an immutable recovery state with
  **separate facts**, not one status word - stop requested, stop **acknowledged** (the
  endpoint answered), **halt observed** (a real Halted/Off status), transport unavailable
  (with the transport's own reason), reset requested, **reset delivery uncertain**, recovery
  verified, homing required, plus the host / session / fingerprint the episode is bound to.
  A successful HTTP send is never treated as a verified physical stop or a verified reset.
  `RecoveryReducer` holds the pure transitions (`StopRequested`, `StopAcknowledged`,
  `StopFailed`, `Observed`, `TransportLost`, `ResetSubmitted`, `ResetDelivered`,
  `ArmOperatorRecovery`, `HomingVerified`), and `RecoveryState.Notice` is the one line the
  window shows about all of it.
- **One reset rule, three callers**: `ResetPolicy.Decide(ResetContext, nowUtc)` is consumed
  by `PrintConsoleButtons` (the footer button and its reason), the Terminal tab's `M999`,
  and `MachineSession`'s recovery transaction, which re-derives it inside the command lock.
  **Path A** is decision D4 unchanged: connected, Halted/Off, trusted, nothing pending.
  **Path B** is new: THIS session's emergency stop plus a machine whose status can no longer
  be read (not connected, or an observed transport fault). Path B does **not** require the
  live trust probe - a reconnect sets trust to Unknown, which is one of the gates that
  locked the operator out - but it does require the binding recorded at stop time: same
  session object, same host, same expected fingerprint, no owner identity conflict. A merely
  disconnected host is therefore not a reset target, and an operator-closed session is not
  one either. Path B arms on the first press and sends on the second, because nothing can
  confirm the halt on its behalf.
- **The window says what is wrong instead of greying out a button.** `PrintConsoleState`
  carries `Recovery`, `SessionId`, `ExpectedFingerprint`, `ExpectationConflict` and derives
  `RecoveryNotice` / `ResetCommand`. The console footer shows the notice in amber in place
  of "last:" (with the full text on the Reset button's own tooltip, since the footer label
  ellipsizes), the Reset button is labelled from the decision (`Reset (M999)` /
  `Recover (M999)` / `Press again`), the `info` output grows a `recovery:` fact
  line and a `recovery note:` line **only while something is happening**, and
  `ConsoleNextAction` offers Reset ahead of "Reconnecting...". The notice for a dead
  endpoint says in words that a button cannot repair a dead connection - enabling one is
  not a fix, and the operator has to know that before pressing again.
- **The transport seam reports what it observed.** `IMachineClient.ResetAsync` now returns
  `ResetDelivery` (acknowledged / uncertain, with a detail). `DuetPollClient.ResetAsync`
  previously caught **every** `HttpRequestException` and returned as if the reset had
  happened; "the board resets before answering" and "the endpoint is gone" are the same
  exception, so that reported success for a delivery nobody had observed. Both are now
  uncertain; a refusal the endpoint actually answered (an expired session answering 401
  twice, any error status, an explicit `err`) still throws. `MoonrakerClient` reports the
  same three outcomes for `firmware_restart`. To make the classification structural rather
  than message-based, RRF's `SendAsync` now carries the HTTP status on the `DuetException`
  it throws, as `MoonrakerClient` always has.
- **Recovery is confirmed by observation, never by the send.** `MachineSession.ObserveRecovery`
  folds every completed poll: a real Halted/Off status supplies "halt observed", and a
  machine answering on a **newer connection generation** with an acceptable identity
  supplies "recovery verified". After a reset the session discards its state
  (`_latest`, trust, the initiated job) and invalidates the arm configuration, so verified
  homing is required before motion; `start`, `jog`, `goto`, `capture` and **`resume`** all
  refuse until the reset is confirmed and the machine homed, and no job is ever resumed
  automatically. Home stays open throughout - homing is the recovery path out of an unknown
  configuration.
- **An emergency stop clears the queue.** `MachineSession.BeginEmergencyStop` cancels the
  commands queued on and running inside the command lock (a replaceable abort token linked
  into `RunCommandAsync` / `RunGatedCommandAsync`) and opens a new **action epoch**.
  `PrintConsoleReducer.ActionStarted` stamps the epoch, `ActionFinished` takes it and
  **drops a completion that a newer action superseded**, so a jog that was already in flight
  cannot dispatch after the stop, cannot clear the stop's pending state, cannot overwrite
  its result and cannot release the session lease behind its back.
- **The Terminal tab is still not a bypass, in either direction.** A console-entered `M999`
  takes the same `ResetPolicy` decision as the button and then runs the button's own
  recovery transaction rather than a raw send, so the two cannot drift apart in policy or
  in route. Its own two-press confirm arming is unchanged (a blind recovery therefore
  confirms twice, which is the intended friction). The transaction's Halted/Off re-check on
  the raw advanced path is kept as defence in depth.

**Decisions**

- **D6: an acknowledgement is not a stop, and a send is not a recovery.** The three states
  the transport can honestly report are acknowledged, uncertain and refused. Everything the
  console says about a physical stop or a completed reset comes from a later observation.
- **D7: Reset relaxes the live trust probe for a session's own emergency stop, and nothing
  else.** The identity binding is preserved by recording host, session and expected
  fingerprint at stop time and re-checking them, so the relaxation cannot turn an unrelated
  unreachable host into a reset target.
- **D8: an E-Stop episode closes.** Once the machine is back and homed - or simply answers
  normally again on a new connection - the recovery state goes quiet, so one emergency stop
  cannot authorise a blind reset for the rest of the session.
- The bounded recovery transaction waits at most `MachineSession.RecoveryQueueWait` (5 s)
  for the command lock and then refuses by naming the reason, rather than queueing behind a
  stuck motion command. Its prerequisite is a full object-model poll of its own; a poll that
  fails is recorded as a transport fault and only the armed operator recovery continues.
- Capability-specific throughout: Duet sends `M999`, Moonraker `firmware_restart`, and the
  labels, refusals and notices name whichever the transport uses. Klipper keeps its
  Halted-only rule on the readable path (`MachineCapabilities.MaintenanceReset` is untouched
  and still governs the hidden Jog component's armed any-state override).

**Tests** - Core 1355 to 1389 (34 new, all green), FrameworkSmoke 409 per TFM
(net48 / net7.0 / net7.0-windows) unchanged, tooling 27 unchanged. New
`IAMLabSlicer.Core.Tests/RecoveryTests.cs` covers the plan's acceptance list: halt with live
HTTP, connection loss after E-Stop, expired authentication (401 twice is a refusal, not an
uncertain delivery), a busy queue, uncertain delivery, reconnect verification, stale
completion callbacks, and a printing machine that cannot reach Reset by any path - plus the
host/identity binding, the identity conflict, the episode closing, the Klipper command
naming, the `info` projection and the Terminal parity.

### 14. Telemetry integrity, continuity policy, job identity, diagnostic capture (2026-09-09)

Answers section 2 of `docs/dev/OBSERVED-ISSUES-PLAN_2026-09-09.md` and the five follow-up
tasks of its "Revised diagnosis". The incident it is built around: the 2026-09-09 dome job
log holds seven isolated samples 10.55 to 18.41 mm off the same-Z G-code contour (CSV
sequences 397, 405, 453, 492, 528, 535, 595), each flanked by samples less than 0.15 mm from
the path, within layers, Z unchanged, file position advancing, at reported speeds of 37 to
50 mm/s against 43 requested. The operator confirms the robot did not make those excursions:
they are false REPORTED positions, already present in the raw CSV upstream of any viewport
interpolation. **The stage that produced them - controller, transport, parsing or
publication - is still not localized**, because the per-poll HTTP bodies were not retained.
Everything below either removes a way the software itself could invent a position, or makes
the next occurrence carry the evidence needed to point at a stage.

**Strict axis validation.** `JsonValue.Num` maps a missing field, a string or an object to
zero and a boolean to 0/1, and the object-model parser only rejected non-finite values, so a
response that simply omitted `machinePosition` produced a well-formed sample at the machine
origin. A position axis now needs a finite JSON **number**; a rejected X/Y/Z is left out of
`ObjectModelSnapshot.Axes` entirely, where every consumer of `Axis("X")` already fails
closed, and the snapshot carries `PositionValidity` (`Valid`, `Unreported`, `MissingAxis`,
`NotNumeric`, `DuplicateAxis`) with a reason. `MachinePosition` / `UserPosition` are null
unless the position is valid. Both RRF paths and the Klipper `toolhead.position` path apply
the same rule. Homing readiness is deliberately NOT coupled to it: `AllHomed` keeps its
meaning ("every visible reported axis is homed") and position readability is a separate
fact, so no existing gate changes behaviour by accident.

**Acquisition identity and timing.** Every snapshot can carry an `AcquisitionStamp`: a
process-monotonic id, the request-start and response-received timestamps **of the coordinate
request specifically**, the connection generation, a composite flag and the page count of a
stitched `rr_model` array. The modern path stamps `move.axes` and marks the observation
composite (state, axes and job are sequential requests); the legacy `rr_status` path is one
response and is not composite - the `rr_fileinfo` name lookup after it is cosmetic and does
not move the timestamps. `TakenUtc` keeps working for existing consumers but now means the
coordinate response's arrival whenever a stamp exists, instead of the end of the parse.

**One publication gate.** `MachineSession.TryPublishLatest` makes `Latest` monotonic in the
acquisition id. The poll loop and `RunGatedCommandAsync` are not ordered against each other,
so an acquisition that started earlier could finish later and hand every consumer a position
from the past. A refused snapshot is still acted on (a gate must decide on the state it read)
and still recorded; it just does not become the published one. This is the smaller of the two
options in the plan - gated-command snapshots keep reaching consumers when they are newer.
It is not claimed to explain the dome spikes; retention received its poll-local snapshot
either way.

**Reusable continuity policy** (`Core/Duet/TrailContinuityPolicy.cs`). Input: validated
observations with acquisition id, timestamps, connection generation, run id, coordinates,
homing flags, status, file position/fraction, requested/observed speed and raw extrusion.
Output per observation: a segment id, a classification (`Printing`, `Travel`,
`StartupOrFooter`, `Paused`, `Jogged`, `Unknown`) and a quality flag (`Valid`,
`SuspectPathDisagreement`, `SuspectSpeed`, `Invalid`, `Discontinuity`), plus the same-Z path
distance, the implied speed and a run length of consecutive disagreements. A new
run/connection, an out-of-order acquisition, an invalid position, homing, a lost homed state,
relative coordinate mode, a time gap over 5 s, a file-position or fraction rollback, a
coordinate jump over 250 mm, or an implied speed over requested x4 + 20 mm/s (or over
1000 mm/s) starts a new segment. A moderately high implied speed flags without splitting.
Every threshold uses the ACTUAL elapsed time. Nothing is ever edited, projected, smoothed or
deleted.

Path disagreement is a **diagnostic trigger only**: over 5 mm from the intended path at the
sample's own elevation marks the sample suspect and preserves it, and deliberately does NOT
break the segment - breaking it would hide the excursion by turning it into two tidy runs.
A sustained disagreement therefore stays flagged sample by sample, with a rising
`ConsecutivePathDisagreements`, so a real tracking fault cannot be read as a handful of
isolated glitches. The comparison uses a new `Core/Duet/SameZPathIndex.cs` rather than
`LivePathDeviation`: 3D nearest distance answers a different question and understates a
within-layer excursion - for the worst dome sample the nearest place in 3D is on the NEXT
layer at 18.23 mm while its own layer is 18.41 mm away.

**Applied in the recorder and in Live.** `PrintLogRecorder` runs the policy on every observed
poll, including the ones no row is written for, and stamps each row. `LiveViewportController`
runs it before `AppendObservation`, splits the drawn run on a segment break and skips an
observation with no usable position - with the break guaranteed by the policy, so the trail
is never stitched across the hole. Live's run identity is the session's retention run id, so
the drawn runs split exactly where the job log's do.

**Versioned CSV.** New columns are appended after the schema-1 ones, so the original column
order is untouched and `PrintLogCsvReader` still imports an old file:
`log_schema` (2), `run_id`, `segment_id`, `quality`, `classification`, `quality_reason`,
`path_distance_mm`, `implied_speed_mms`, `acquisition_id`, `position_valid`,
`position_invalid_reason`, `composite`. The version rides in a per-row column rather than a
banner line, because the reader takes the first non-blank line as its header. A row with no
usable position writes **empty** x/y/z and `position_valid=0` instead of zeros, and the
reader keeps such a row instead of skipping it; a row with missing coordinates and no such
declaration is still malformed, as before.

**Immutable job snapshot** (`Core/Duet/JobSnapshot.cs`). Exact bytes (copied in, handed out
only as copies), SHA-256, parsed path revision, remote path, source
(`ConsoleInput`/`MachineFile`/`External`) and a unique run id: `print.gcode` is overwritten
on every upload, so a file name is not an identity and the same file printed twice is two
runs. `JobIdentityTracker` keeps the PREPARED job apart from the ACTIVE one - editing the
Console input during a print changes only what a later Start would run - and
`PrintConsoleState` gains `PreparedJob`, `ActiveJob`, `EffectiveJob` and
`IntendedPathAvailable` (additive fields and two `With…` copies only). An externally started
job has no intended path until its file is retrieved and verified; the Console's own input is
never substituted.

**Bounded raw-telemetry diagnostic window** (`Core/Duet/RawTelemetryWindow.cs`). A ring of
the last 200 per-poll observations, each with the untouched response body (capped at 4096
characters, with the real length and a truncation flag), the endpoint and API mode, both
request timestamps, the acquisition/poll/connection ids, machine and user coordinates,
homing flags, job identity and file position, reported speeds, arm configuration, and the
parsed position with its validity and the continuity verdict. `DuetPollClient` raises the
body before parsing (`RawBodyObserved`), and only for the request that carries coordinates,
so the metadata around it cannot move the observation in time. A suspect/invalid/discontinuous
verdict, a transport failure, a reconnect or an explicit `MachineSession.NoteDiagnostic` arms
a capture of the 200 polls before it and the 40 after - every poll, not every fifth, because
the dome spikes sit between exported CSV rows. Captures are serialized one JSON object per
line and written by the **retention worker thread**, never the poll loop, into a new
`diagnostics.jsonl` beside `print.csv` in the job's staging directory, mirrored and finalised
to the destination like the other two streams (`JobLogManifest` version 2 adds
`diagnosticsOffset`). Bounds and drop counts: a 5000-entry share of the retention queue with
`LogRetentionService.DiagnosticsDropped`, a 4000-line in-memory session window with
`SessionDiagnosticsDropped` that stays readable after the job log closes, plus the window's
own `Overwritten` counter and a per-capture `overwrittenBefore`, so a short window is never
mistaken for a quiet machine.

**`manifest.complete` is not a successful print.** It only ever meant the LOG finished; a
cancelled, halted or connection-lost run finalises its log exactly like a completed one. The
manifest and `JobLogEntry` now also carry `Outcome` (the terminal machine state or finish
reason), set from the run-end record. A version-1 manifest reports `null`, which must be
displayed as unknown, never as success.

### 15. Print bed contract, bed shapes, legacy migration, one-sentence descriptions (2026-09-09)

Plan `docs/dev/OBSERVED-ISSUES-PLAN_2026-09-09.md` section 3, from the maintainer's two
requests: "Duet live and the robot simulation should take the same input for the print bed.
All components should just need the `bed` input which sets center point, width and depth as
well as form and is only configurable in the print bed component", and "descriptions of the
components is too long".

- **One plate, configured in one place.** Live View lost `bedWidth`, `bedDepth` and
  `bedCenter`; Robot Simulation lost its profile-specific fallback plate; Calib Points lost its
  `bedCenter`/`bedWidth`/`bedDepth` filter group. All four consumers - Live View, Robot
  Simulation, Place and Calib Points - now read the plate from `bed` and nothing else, and
  `bed` is a core input on each, not an opt-in group. **An unwired or unparseable definition
  draws no plate** and says so as a remark ("connect an IAMLab Print Bed component to 'bed'").
  An invented plate that looked exactly like a configured one was the whole defect: Live and
  Simulation held different literals for the same physical bed.
- **Shape, versioned.** `BedDefinition` carries `BedShape { Rectangle, Ellipse }`; equal width
  and depth make the ellipse a circle, and there is deliberately no separate circle case to get
  out of step with it. Arbitrary boundary curves remain a follow-up. A rectangle still
  serializes as `iamlab-bed:v1:…`, byte-identical to 4.0.0; an ellipse serializes as **v2** with
  `;shape=ellipse`. The version has to rise **because** an older parser ignores unknown keys and
  would read an ellipse as a rectangle - silently, and 200 mm out at the corners. v1 continues
  to parse as a rectangle. `shape` accepts `rect`/`rectangle`/`0` and `ellipse`/`circle`/`1`, so
  the component's integer input and a hand-written string cannot mean different things.
- **Outline geometry in Core, drawn once.** `BedDefinition` gained `Contains`, `Outline`,
  `Bounds`, `SpanX`/`SpanY` and `GridLines` - pure millimetre maths, no Rhino. `BedPreview`
  builds the plate, the printable shading, the outline, the axes and the grid from them, so
  Live View and Robot Simulation cannot draw different beds from one definition. A round plate
  gets a radial shading mesh and an extruded apron instead of a square one; the rectangle path
  is unchanged. `CalibrationSequence` filters its marks through the same `Contains`, following
  the shape through the machine-frame mirror about `y = -x` (which maps an axis-aligned ellipse
  onto an axis-aligned ellipse with its spans swapped, exactly as it already did for the
  rectangle). Document units convert exactly once, on the Print Bed component's point inputs,
  and back at each consumer's drawing and output boundary.
- **Reach is still the robot's.** The bed is the physical plate; the reachable region belongs to
  Robot Definition. Robot Simulation still takes the annulus from the profile, Live View still
  from its own kinematics overrides, and neither reads `rmin`/`rmax` off the wire.
- **Print Bed** gained an appended `shape` input (integer, 0 rectangle / 1 ellipse) with a value
  list, and its `outline` output is now the Core outline converted back to document units.
  `bed`, `width`, `depth`, `center`, `printCenter` and `info` are unchanged; `info` names the
  shape.
- **Place keeps `printCenter`.** It is a placement operation - where *this* part stands - not
  bed configuration, so it stays and still wins over the bed's default when wired. The plate
  centre and the default part-placement centre remain two different quantities, both configured
  on Print Bed, exactly as ARCHI 12.1 requires.
- **Hidden components:** the five hidden Duet components (Connect / Status / Jog / Terminal /
  Print) expose **no** bed configuration - Jog only *outputs* a captured `bedOrigin` point - so
  they needed no compatibility work. The hidden `IAMLab Robot` keeps its own frozen
  width/depth/centre sockets and now drives the shared preview through a rectangular
  convenience overload; its only code change is that a non-positive width no longer produces a
  degenerate plate (its `bed` output is null instead).

### 17. Live View: toolpath only, no extrusion, no marker, no log; one redraw per tick; job from the Console (2026-09-09)

Answers section 4 of `docs/dev/OBSERVED-ISSUES-PLAN_2026-09-09.md` and the Live-side remainder
of its section 2, from four maintainer requests: "Smoothened do not show the point and the
delay/sample age next to the nozzle, take the gcode from console output", "Remove the extrusion
showing in the live component, as this one should only visualize the toolpath directly live",
"The live component does not need a job log as this is done in the console directly and streamed
to a folder", and "The live view is lagging the canvas as well as the simulation in the specified
reloading (eg 300 ms)".

**Live View draws a toolpath.** The posed robot, the wired print bed, the effective job's
intended path as thin neutral context, and the observed trail. Three things left:

- **The extrusion surface.** `extWidth` and `layerHeight`, the bead cache, the
  fraction-to-mesh mapping and the bead draw call are gone from `DuetLiveViewComponent`,
  `LiveViewportController` and `LiveRobotConduit`. A bead preview belongs to the G-code
  Generator and Robot Simulation; Live visualises what the machine is reporting.
  `Ui/ExtrusionPreview.cs` itself is untouched - Robot Simulation, the hidden Robot
  component, Interlayer Time and Print Stats all still use it, so nothing in Core or the
  plugin became dead.
- **The nozzle marker and the text beside it.** `LiveRobotConduit` drew a point at the tool
  unconditionally and `BuildFrame` generated
  "observed / smoothed - delay N ms, sample age N ms" next to it. Both are gone.
  `LiveRobotFrame.Label` became `Reason`: it is never drawn and never compared, because the
  changing age string alone made an otherwise identical frame compare unequal and forced a
  Rhino repaint on every tick of a motionless machine. **A stale pose is still unambiguous**:
  the arm is drawn as the existing translucent ghost, and `info` says
  "STALE, arm drawn as a ghost" with the sample age in milliseconds. The Console's own
  diagnostics keep the snapshot age they already carried; no Console output was added or
  changed here.
- **The print path log.** The six `log` inputs, the `layers` / `log` / `path` / `logInfo`
  outputs, the print-log owner registration, the CSV export, the in-memory copy and the
  "Clear print log" menu item are gone. `MachineSession.ConfigurePrintLog` /
  `ReleasePrintLog` and the opt-in recorder behind them are left in place but now have no
  caller: `ObservePrintLog` returns immediately while `_printLog.Active` is false, so the
  cost is one field read per poll. Removing that subsystem is a separate cleanup and is
  listed as owed. **Console-configured retention is untouched and independent**: it is the
  always-on `_retentionLog` recorder fed by `ObserveRetention` on every poll and routed to
  `LogRetentionService`, with no owner registration of any kind, which is exactly what
  `RetentionDiagnosticsTests.SessionRetentionRecordsAWholeJobWithNoLoggingOwner` already
  pins - a whole job recorded, named, outcome-stamped and completed with no logging owner
  registered at all. Live absent, disabled or deleted changes nothing about it.

**A `trail` output instead** (output 7, geometry tree). One branch per continuous drawn run:
a polyline for two or more observations, a single point for a run of one, in Rhino
coordinates through the existing frame map. It is measurement, so it is never smoothed - the
animation's interpolated frames never reach it, only `snap.MachinePosition` does - never
joined across a break the already-wired `TrailContinuityPolicy` declared, never projected
onto the intended path, and it does not require logging to be armed because there is no
logging left to arm. Suspect samples stay in the trail with their raw coordinates and are
counted in `info` (`N suspect (kept raw)`); observations with no usable position are counted
too (`N without a position`).

A run can also end for a reason continuity does not cover, and that is a new rule:
`Core/Duet/TrailChordPolicy.cs`. Two observations can be perfectly continuous and still have
travelled a curved route between them - the 2026-09-09 dome capture's exported rows are a
median 1.94 s apart at 43 mm/s, which draws chords straight across a circular contour. So a
straight segment is withheld when the ACTUAL elapsed time says the machine covered materially
more ground than the chord is long: `speed * dt > chord * 1.25 + 1 mm`, above a 2 mm chord.
At 43 mm/s a 300 ms sample on a 50 mm radius gives a ratio of 1.003 and stays one run; a 2 s
sample on a 25 mm radius gives 1.74 and breaks. Unknown elapsed time withholds the chord;
unknown speed is no evidence against it. Nothing is deleted, moved or smoothed either way -
only the line between the two points is withheld, and both are still drawn where they were
reported. `SegmentId` on a branch still names the continuity segment, so one segment can
contribute more than one branch when a chord could not be asserted.

**The intended path comes from the Console's job.** Live no longer parses an arbitrary input
of its own. `MachineSession.Jobs.Effective` - the active `JobSnapshot` while a print runs, the
prepared one otherwise - wins whenever it exists, and its exact bytes are parsed **once per
revision** by a new `IAMLabSlicer/Duet/ParsedJobCache.cs`: keyed by SHA-256 plus the frame
(a Cartesian definition and the mirrored SCARA frame give different drawn points for the same
bytes), parsed on a thread-pool thread, one parse per key in flight, bounded to four entries
with least-recently-used eviction. The entry carries the machine-frame samples, the decimated
Rhino-frame context polylines (extruding runs only, capped at 40,000 drawn points) and the
`LivePathDeviation` index, all built off the UI and poll threads, so a solve is a dictionary
lookup and a reference assignment. The job's bytes are copied inside the parse lambda, not at
solve time, so a cache hit does not copy a 2.6 MB file.

The `gcode` socket **stays at index 2** as a fallback for a definition that wires the
Console's `gcode` output or a file directly, and it is used only while the session has no
effective job. When the session has one, the job wins and a wire whose lines do not match it
is reported as a remark. When the session reports an externally started job
(`IntendedPathAvailable == false`), **no path is drawn**, `info` says
"intended path: unavailable - job … was started outside this session", and a wired `gcode` is
explicitly NOT substituted (with its own remark). One deviation from the plan's wording: the
"differs" test compares the wire's line-content identity against the identity of the lines the
job was parsed from, so before that parse finishes the remark says "is not used" rather than
"differs from it" - it never claims a difference it has not established.

**Redraw and solve model.** Poll acquisition, animation and GH output publication stay
independent and nothing here calls `ExpireSolution`. The persisted `iamLiveAutoOutputs`
preference and `ExpireMinIntervalMs` are unchanged, so with automatic outputs off a poll
still never solves the canvas. What changed:

- **One Rhino redraw per UI tick, at most.** `PublishFrame` and `PublishOverlaysIfDue` each
  called `Redraw()`, so a tick that moved both repainted twice. They now return whether a
  redraw is owed and `UiTick` issues exactly one, in its `finally`.
- **Frames compare by geometry.** `SameFrame` compares arm visibility, staleness, the nozzle
  position, the link meshes and transforms and the schematic lines. No diagnostic string is
  in a frame any more, so a stationary pose publishes nothing.
- **The pump stops.** A hidden pose, or a stale pose with nothing changed, stops the timer
  outright. A settled pose that is not yet stale drops to a 500 ms beat whose only job is to
  notice staleness, and stops once it has. A new sample or a solve wakes it.
- **The frame budget is 30 fps** (33 ms) by default rather than 60, degrading to 15 and then
  10 fps on frame work p95 over 12 and 25 ms, and recovering only after two seconds of
  headroom - detail is raised when it is affordable, not by default.
- **Model bounds are cached.** `BuildFrame` called `Mesh.GetBoundingBox(transform)` per link
  per frame, and that walks every vertex of assemblies running to roughly 100,000 faces. The
  untransformed box is now measured once per shared base mesh instance and only its corners
  are transformed after that. The conduit's existing caches are unchanged - one coloured copy
  per base mesh, and a paint callback that reads two immutable published states without taking
  a lock or creating geometry - and the trail buffers stay bounded (5000 points, 0.5 mm
  decimation, incremental append).
- **Robot Simulation does not rebuild without a content change.** It re-parsed the G-code,
  re-sampled it and re-ran inverse kinematics on **every** solve, including the ones where
  only the `sim` scrub had moved - and a Console `gcode` output that republished identical
  bytes on a position poll would have rebuilt all of it at telemetry cadence. The derived
  state is now cached under profile + arm mode + width + document scale + source content;
  the scrub is deliberately not in the key. A curve tree has no content hash, so it is
  sampled first and the samples are hashed, which still skips the kinematics.

**The poll interval's meaning is now explicit.** It is a **target start-to-start period**.
It used to be an idle spent AFTER the poll's own requests, so a configured 300 ms with a
200 ms cycle produced a 500 ms observation spacing and the number described nothing the
operator could see. `PollCadencePolicy.WaitAfterWork(target, workElapsedMs)` subtracts the
work already done, clamps to `MinIdleWaitMs` = 20 ms so an overrunning cycle still yields and
still observes cancellation, and never returns more than the target. Requests remain
non-overlapping by construction - the loop awaits them and only then waits - and the
focused-console fast policy (`Decide`, 250 ms) is unchanged and still applies first. Wake
requests are still coalesced by the capacity-one semaphore, and UI callbacks by
`LiveDisplayPolicy`.

On the **slow optional reads**: `DuetPollClient.GetSnapshotAsync` issues `state`, then the
timed `move.axes` that carries the coordinates and the acquisition stamp, and only then the
optional `job`, `move.currentMove`, `move.speedFactor` and the thermal keys. Those therefore
cannot delay the coordinate observation *within* a poll - they lengthen the cycle, which the
start-to-start change now absorbs instead of adding 300 ms on top of it. The lab's RRF 3.1.1
board takes the legacy path, where coordinates arrive in a single `rr_status?type=3` response
and the `rr_fileinfo` name lookup deliberately does not move the coordinate timestamps.
Nothing in the client was changed: giving the thermal reads their own cadence would have
broken `DuetThermalTests.ThermalPollCadenceReadsHeatersEveryPollAndTheToolMapEveryTenth`,
which pins the current contract, and the plan asked to change only what is needed.

### 18. Machine Console: output categories, gcode output, recent prints and verified reprint (2026-09-09)

Answers section 5 of `docs/dev/OBSERVED-ISSUES-PLAN_2026-09-09.md` - the "Fewer Console
outputs", "Live uses Console G-code" and "Recent jobs / reprint" rows - from two maintainer
requests: "Group the output from the Console by categories (to have less output)" and a way
to print an older job again without re-slicing it.

**Twenty-seven sockets became six categories.** The console declared 27 fixed outputs and
set them by index. It now declares them with a category each, and a NEW component registers
only the three a console is useless without. Everything else is one context-menu click away
under "Outputs shown", which lists what each category adds.

| Category | Outputs |
|---|---|
| Connection | `host`*, `connected` |
| Job | `status`*, `state`, `progress`, `jobFile`, `uploaded`, `gcode`* |
| Motion | `pos`, `homed`, `xHomed`, `yHomed`, `zHomed`, `bedOrigin`, `zZero` |
| Validation | `danger`, `problems`, `messages` |
| Temperatures | `hotend`, `hotendTarget`, `bed`, `bedTarget`, `fan`, `speedFactor`, `flowFactor` |
| Logs / Diagnostics | `log`, `info`, `reply` |

`*` = pinned: always registered, whatever the categories say. The default visible set is
therefore exactly `host`, `status`, `gcode` - a host to wire the other Duet components with,
one line saying what the console is doing, and the job itself.

**Decisions.** (1) Per-output pinning rather than a "default-on" category, because the plan
asks for three sockets and no category contains exactly those three. (2) Native Grasshopper
types throughout: a hidden category is an absent socket, never a value flattened into a text
dump. (3) Names are never renamed - a saved document reconnects wires by socket name, and
the contract baseline pins them. (4) The machinery is generic
(`OutputSpec`, `OutputToggleGroups`, `OutputContractVersion` on `IamComponentBase`), mirroring
the input groups the bed work extended, so a second component can adopt it without new code.

**Migration rule: a wire is data.** An archive written before this is reconciled once, in a
scheduled solution after the document has finished loading and its recipients have resolved
(the same hook `MigrateRetiredInputs` uses on the input side, armed by a separate
`iamOutputContract` key so it runs exactly once). Every category that has a WIRED socket is
switched on; only unwired sockets are unregistered; nothing carrying a wire is ever removed,
and the component says which categories it kept and why. Hiding a category by hand follows
the same rule: it is refused with a remark while one of its outputs is connected. Active
categories persist in `iamActiveOutputGroups`.

**Emission by name.** `Emit` sets values through `SetOut` / `SetOutList`, which map a name to
the current index. An index would have published a temperature into a point socket the first
time somebody hid Motion. `tests/tooling/test_console_parity.py` now fails the build if a raw
`DA.SetData(` reappears in the console's `Emit`.

**The expire policy compares only what exists.** `OutputSnapshot` carries an
`OutputVisibility`, and both `Equals` and `GetHashCode` skip a hidden output entirely. With
Motion and Temperatures hidden, a position poll and a drifting hotend produce an EQUAL
snapshot and no re-solve at all; showing a category is itself a change, so the outputs
refresh at once. The 1000 ms coalescing and the never-while-`live`-is-off rule are untouched.
`PrintConsoleOutputs.From` also stops BUILDING what is hidden - the multi-line `info` summary,
the log tail and the decoded G-code - so a compact console does not pay for twenty-seven
outputs.

**The `gcode` output** publishes the EFFECTIVE job: `ActiveJob` while a print runs, otherwise
`PreparedJob`. Editing the wired G-code during a print therefore changes what a later Start
would run and nothing on this socket. The lines come from the job snapshot's own bytes
(`JobSnapshot.Lines()`, decoded once and cached on the immutable snapshot), and value
equality compares the job's SHA-256 rather than 58,000 strings, so a status poll can never
look like a changed job. A print started outside this session has unknown bytes: the socket
publishes an EMPTY list plus a remark saying so - never the Console's own input in their
place. Section 14 defined `JobSnapshot` / `JobIdentityTracker` and `MachineSession.Jobs` but
wired nothing; the wiring is completed here - `Prepare` on a changed input or a history
selection, `StartPrepared` inside the confirmed Start transaction, `StartExternal` when a job
appears that this session did not start, and `EndRun` when the run ends. The session's

silently refuse a pose. Nothing is clamped, projected or substituted: the raw coordinates go on

**V2. The renderer was drawing an incomplete file.** `ext[k]` describes the segment ENDING at
point k, but `BuildContextRuns` walked POINTS and skipped every point whose own flag was false:
for A/B/C with flags false/true/true it emitted B and C, losing A to B - the first segment of
every extrusion run - and a single-segment run vanished entirely. Travel, seam and coast moves
were skipped by design. That is the operator's "seams and travel moves are missing".

**V3. The seam splits were not travel classification.** Live never consults
`verdict.Classification`; the splitter was `TrailChordPolicy`, comparing requested speed times
