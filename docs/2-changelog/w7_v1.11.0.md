## Changes

A job can re-raise acceleration and jerk past what the machine was deliberately
configured to tolerate, and nothing warned. `GcodeConfig` carries `AccelXY`/`AccelZ`/
`AccelE` plus jerk, and `GcodeBuilder` writes them into the job header as `M201`/`M566`.
The lab Potterbot's acceleration was **deliberately reduced** to `M201 X800 Y800 Z500`
from the vendor's `X3000 Y3000 Z2000`, because its external drivers stall — so a job
carrying vendor defaults would silently undo a safety decision.

This release compares the job being uploaded against the machine's configured baseline,
evaluated inside the gated transaction.

### Where the baseline comes from, and why not a live probe

`0:/sys/config.g` is read once per connection and treated as the immutable baseline. A
bare `M203`/`M201` query would report *mutable current state*: jobs emit `M201`/`M566`
and never restore them, so after one over-raised job the probe would read the raised
values as the baseline and permanently disarm the warning. `config.g` is the deliberate
intent and cannot be poisoned by a job.

Both sides of the comparison are therefore G-code, where units are fixed by the spec:
`M203`/`M566` in mm/min, `M201`/`M204` in mm/s². Normalization happens once, at the
parse boundary.

**The `M203 S1` exception bites.** `M203 S1` switches the command to mm/sec, matching
RepRapFirmware's own `S1` test. A scanner that always divided by 60 would read
`M203 S1 X100` as 1.67 mm/s and miss a job raising the ceiling sixty-fold. Both the
config side and the job side honour it.

### Severity policy

- A job raising **acceleration or jerk** over the baseline is a **warning** — geometry
  is unaffected but the hardware limit was chosen for a reason.
- A job raising **`M203`** is a **warning**: it removes firmware clipping.
- A requested per-axis **feedrate above an intact `M203`** is **informational**. RRF
  clips the move by scaling all axes together, so extrusion per mm — and therefore bead
  geometry — is unchanged; only the time estimate is wrong.
- `blockWarnings` refuses on warnings; informational findings never refuse.
- A missing or malformed `config.g`, or a failed live probe, is reported as **unverified
  and never blocks printing**. An unreadable diagnostic must not become a new refusal
  path.

### BREAKING — the `gcode_text` output was removed

The G-code component lost output index 1 (11 → 10 outputs) and Restart lost its own
(6 → 5). That single concatenated string was the cause of canvas hangs on large jobs.

**Every wire after `gcode` shifts up one position.** Grasshopper reconnects by index and
reports nothing, so this is silent. Open every existing definition and confirm
`preview` / `travels` / `length` / `info` still feed what they used to. The definitions
in this repo to check are `docs/Debug_script.gh` and `docs/Example_script.gh`.

### Also in this release

- `M203` is accepted by `GcodeParser`'s non-motion allowlist — without it the warning
  path was unreachable, because a job containing `M203` failed closed before it could be
  compared.
- `DuetSessionManager.HasOwner` fixes a session-ownership defect: matching the cached
  host was not proof of ownership. `Disconnect` calls `CloseHost`, which drops every
  owner while each surviving component still holds `_leasedHost`; on the next `Connect` a
  host-only check returned early and left those components unregistered, so the Connect
  component looked like the sole owner and its Release could stop a session others were
  still using.
- `LastActionWarned` carries severity explicitly. `RunGatedAction` wraps a successful
  reply as `<action> @ <host> - confirmed by Duet: <reply>`, so an embedded `WARNING:`
  never reaches the front of the string — the prefix test demoted every non-blocking
  motion-limit warning to a grey remark, which is the one thing that warning exists to
  avoid.
- The connect-time kinematics probe reports *why* it failed (`KinematicsProbeDetail`)
  instead of a generic message, and says to reconnect to retry.
