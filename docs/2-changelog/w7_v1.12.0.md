## Changes

Two defects found in the 2026-08-25 lab session, both of which made the plugin
misrepresent the machine to the operator.

### The simulated arm was the mirror image of the real one

`M114` after a full `G28` reports `X:200 Y:-500 Z:400` with joints **-18.489 / -116.054**
(`docs/6-memo/lab_2026-08-25_final-bringup.md`, Step 11). A negative distal angle is arm
mode **1**. Every component defaulted its `elbow` input to **0**.

At that pose both arm modes satisfy the firmware's `A-41.1:319.1` / `B-151.2:151.2`
limits, so `InverseRrf` never fell back to the other branch — it returned the one it was
asked for. Nothing errored. The arm was simply drawn reflected about the line from the
origin to the nozzle, with the elbow at `(-256.9, -485.2)` instead of `(520.8, -174.1)`,
which reads as a large rotation rather than a mirror. That is the reported "swapped X and
Y / off by 90 degrees" appearance.

Worse, the same wrong preference was recorded as machine truth: after a verified full
`G28`, `DuetJogComponent` seeded the arm-configuration replay from the operator's `elbow`
input, even though the trigger pose it replays from is built at the endstop joint minima —
where the distal minimum fixes the branch outright.

**The homed arm mode is now machine state, not a preference.** `robot.xml`'s `<HomePose>`
carries an optional `armMode` attribute (`1` here, with the measured joints recorded
beside it), which flows to `RobotLimits.HomedArmMode` next to `CalibratedHomePose`. Three
sources now decide the arm mode, in order:

1. the session's tracked `{armMode, thetaTurns}` from a verified home;
2. `HomedArmMode`, whenever a path is anchored by a `G28`;
3. `elbow`, only where nothing anchors the walk — a program with no `G28`, `JogPlanner`
   before a home, `CalibrationSequence` generation, and the `ScaraFit` solve.

Both seed sites in `RobotChecks.Run` were changed, via one shared helper. Changing only
the mid-program `G28` reseed would have fixed nothing for an ordinary job: a conforming
job homes *before* its first move, so the post-home pose is evaluated from the **initial**
seed and never reaches the teleport branch.

`Duet Live` was the only IK call site in the repository still using the textbook
`ScaraKinematics.Inverse` with a raw `elbow` int and ignoring the session entirely. It now
uses `InverseRrf` with the tracked configuration.

**`Duet Live` deliberately gained no homed-state check.** After `M112` then `M999`, RRF's
motor counts reset and the board reports `theta = psi = 0`, which is `X = L1 + L2` — a
fully extended arm. That render is *correct*: it is what the firmware believes, and the
view's job is to show the machine as reported, not as assumed. `info` now reports
`axes homed: yes/no` as a diagnostic. Homing restores the pose.

### A refused control component said nothing at all

Connected but not yet homed, the Print component greyed out every button except E-STOP
and displayed no text anywhere. The refusal reason existed — but only as a capsule
*tooltip*, which is invisible to an operator looking at a component that has simply
stopped responding. E-STOP stayed live because it bypasses the gate by design, which made
the component look selectively broken rather than gated.

Every control component now raises the active refusal as a runtime message.
Severity is declared by the component that *produces* the reason, never matched out of
its text:

- **Warning** — machine-state and safety refusals: arm configuration Unknown, a failing
  job gate, `StateGate` refusals (not idle, not homed, stale poll), a home macro that is
  unavailable, a file belonging to the running job.
- **Remark** — not connected, busy, and rejected terminal input (parse failure, not on the
  diagnostic allowlist, expert unlock required).
- **Silent** — routine prerequisites: "validate the job first", "select a file first",
  "enter one G-code line", "generate at least one calibration point", "already connected".
  An idle canvas must not be permanently orange.

Each component computes its reasons in one helper shared with `ButtonRows`, so a tooltip
and its message cannot disagree. The message clears by itself: Duet components are not
`Heavy`, so `Compute` re-runs on the `SessionChangeKind.Status` that
`SetArmConfiguration` already raises — a successful `Home all` both re-enables the buttons
and removes the warning, with no manual recompute.

## Backward compatibility

- **`elbow` defaults changed 0 -> 1** in all six components. A definition with a **wired
  or internalised** `elbow` keeps its stored value; a definition with an **unwired**
  `elbow` changes from up to down on reopen. That is the intended correction.
- **Any job that starts with `G28` now takes its arm mode from the machine**, regardless
  of the `elbow` input — so results change for those definitions too. This is a behaviour
  change, hence a minor version rather than a patch.
- `robot.xml`'s `armMode` attribute is **optional**; an older resource parses unchanged
  and falls back to the `RobotLimits` default. An invalid value is rejected with a parse
  warning rather than being silently read as mode 0.
- No `ComponentGuid`, input, output, or persistence change. `LimitsKey` gained
  `HomedArmMode`, which forces a one-time recompute of cached robot checks on first solve
  after upgrade — intended, since the cached results were computed in the wrong branch.

## Testing

- **Build**: clean on `net48`, `net7.0`, `net7.0-windows`, 0 warnings.
- **Tests**: 631 passing, 18 new. No existing test broke — which is itself the finding:
  nothing pinned home-anchored arm mode before.
- The new tests are **provenance tests, not self-consistency checks**. The expected joints
  are the machine's measured `M114` values, and a counterpart case flips `HomedArmMode` to
  prove the seed is what drives the branch rather than a hard-coded constant.
- **Not automated**: the gate reporter and the Live-view branch selection are both
  plugin-layer. Five on-machine rows added to `docs/dev/TESTING.md`, and both paths
  recorded in `docs/4-unit-tests/COVERAGE-DEBT.md`.

## Known limitation (recorded, not fixed)

The verified-home trigger pose is computed at `(J1Min, J3Min)`, but the home macros step
off the switches by 5 degrees, so the true pose is about 45 mm away (`r` 265 -> 305 mm).
`HomeMacroReader` parses only Cartesian moves, so the raw-motor step-off is invisible to
it. Harmless today — both poses clear `R235`, and `-146.2` is still negative, so the
arm-mode conclusion is unchanged. Logged in `docs/6-memo/BACKLOG.md`.
