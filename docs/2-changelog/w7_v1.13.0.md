**Release Date**: Week 7, 26-08-2026

## Changes

Defects reported from the lab on 2026-08-26, all of which made the plugin disagree with
the machine standing next to it. Section 1 was confirmed on the machine and sections 2
and 3 follow from that same session.

---

### 1. The machine's Cartesian frame is the Rhino frame mirrored about y = -x

**Reported**: the arm shown in `Duet Live` is not where the real arm is. The firmware
reports the post-home pose as `X200 Y-500 Z400`; the operator sees that same physical
point at Rhino `X500 Y-200 Z400`.

Those two readings are related by

```
machine (x, y, z)   <->   Rhino (-y, -x, z)
```

which is a **reflection about the line y = -x**, not a rotation - no rigid rotation maps
`(200, -500)` to `(500, -200)`. The plugin had treated the two frames as identical.

**Maintainer directive**: the Rhino design frame is ground truth. Geometry, G-code and
robot movement are all expressed in it, and the machine frame exists only where the
machine itself demands it.

New `IAMLabSlicer.Core/Geometry/MachineFrame.cs` is the single definition of the map. It
is its own inverse - one negation pair converts either way, and a round trip is bit-exact
because negation is exact in IEEE-754. Zero is kept positive so nothing formats as
`-0.000`.

**Where the conversion lives.** The rule is a split by *purpose*, not by project:

| Stays in the machine frame | Converted at the boundary |
|---|---|
| `ScaraKinematics`, `RobotChecks`, joint ranges | Curves in, previews out, point outputs |
| The M208 envelope (`RobotLimits.XMin…YMax`) | Bed plate, printable area, problem markers |
| `GcodeParser`, `JobGate`, `JogPlanner` | Jog capsule directions, `pos` / `bedOrigin` |
| G-code text, Duet telemetry, `homeall.g` | Posed robot meshes, trail, print-log path |

Anything that validates or commands the machine keeps the machine's own numbers, so it
can still be audited against `config.g` line for line. Everything a person draws or reads
is Rhino.

Concretely:

- **`GcodeBuilder`** works in Rhino throughout - toolpath, skirt, seam logic, previews,
  `StartPoint` - and maps only in its four emitters. Because the map is a reflection it
  also reverses arc sense, so `G2 <-> G3` and `I/J` swap with it.
- **`RobotComponent`** validates G-code in the machine frame (it arrives that way) and
  converts curve input on the way in; every drawn thing converts on the way out. The
  printable-area shading maps each sample before testing the M208 box, because that box
  is not symmetric under the map.
- **`RobotModel`** poses the assembly at *reflected joint values* rather than reflecting
  the meshes - same joint centres, true part handedness. See section 2.
- **`Duet Live`** runs IK on the raw telemetry, so `J1`/`J3`/`J2` still publish the
  machine's own joint angles, and converts only what is drawn. Per the directive, the arm
  is drawn as the true machine configuration reflected into the Rhino frame.
- **Jog** capsules are labelled in Rhino and convert the requested delta. The map sends
  one axis to one axis, so `JogPlanner`'s "one axis per press" rule is untouched.
- **`ScaraFit`** converts *both* point lists. Converting only one would leave a reflection
  in the residual, and a rigid grid model (offset + rotation) cannot fit that.
**Behaviour change - check your definitions.** Bed defaults are now Rhino: centre
`(468, -441)`, `bedWidth` 1000 along Rhino X, `bedDepth` 700 along Rhino Y. Saved
definitions keep their own values, which were machine-frame - re-enter them, or re-capture
`bedOrigin` with Jog.

### 2. The drawn assembly: what J1 swings, and which way the parts face

Two separate problems, found by looking at the viewport next to the machine on
2026-08-26 once the motion was confirmed correct.

**The Z-rail swings with J1.** An intermediate build of this release made the rail static
on the reading that the Schiene is bolted to the Fundament. It is not: J1 turns the whole
rail about the pivot together with the proximal arm that rides it, and only the Fundament
stays put. `robot.xml` is back to
`base -(J1)- mast -(J2)- carriage -(fixed)- link1`. A vertical lift commutes with a
rotation about a vertical axis, so the nozzle is identical either way and
`SelfCheck_ShippedRobotXml_Passes` never moved.

**The parts were drawn inside out.** The first cut of the frame map reflected the
assembly meshes and conjugated each pose transform. That put every joint centre in the
right place but mirrored each solid, which on the asymmetric Fundament (302 x 360 mm
footprint, reflected to 360 x 302) read as a 90-degree rotation.

Reflecting a planar arm is the same as posing it at reflected joint values - the
reflection maps a direction at angle `phi` to `-90 - phi`, so `J1 -> -90 - J1` and the
relative elbow angle simply negates. `RobotModel.DrawnJoints` does that instead. Every
joint centre lands in exactly the same place, no mesh is mirrored, and no mesh has to be
flipped on the scrub hot path. Callers still pass, and still publish, the machine's own
joint values. `MachineFrameTests.ReflectingTheArmEqualsPosingAtReflectedJoints` pins the
identity for the nozzle and the elbow.

**The base placement moved into the model file.** The Fundament is the one link no joint
drives, so its rotation and XY offset are its whole pose, not a correction on top of one -
model data, and it now lives in `robot.xml` as `<BasePlacement rotDeg offsetX offsetY>`
next to the joints instead of as constants in the renderer. `RobotDefinition` parses it;
`RobotModel.BakedBase*` survive only as the fallback for a definition that predates the
element. The values were checked against the machine on 2026-08-26 and the 2026-07
calibration held: `-180`, `(3, 82)`. Because the registration is a pure translation the
rotation reads straight off the viewport - positive is counter-clockwise seen from above,
the offsets are Rhino XY millimetres. Drawing only; nothing here reaches validation.
The `PosedMeshes`/`PosedFeatureEdges` overloads that take an explicit placement remain as
the re-calibration entry point.

### 3. Arm configuration stayed `Unknown` after every home

**Reported**: "jogging refused - arm configuration is Unknown; complete a verified home
first" and the matching validate/upload/start refusal never cleared, even after homing.

`homeall.g` was rewritten on the board on 2026-08-25 to delegate with
`M98 P"0:/sys/homez.g"`. `HomeMacroReader` tokenised every line as `letter + number`, so a
quoted macro path was "an unsupported token" - the parse failed on line 1 of the real
file, `PrepareHomeConfigurationAsync` threw, and the configuration stayed `Unknown`
forever. Reproduced before the fix:

```
parse ok=False  err=homeall.g line 2: contains an unsupported token
```

Every gate that depends on a known configuration then refused, correctly, with no way for
the operator to satisfy it.

**Fixed**: `HomeMacroReader` follows `M98 P"…"` calls through a resolver, and
`DuetSession` breadth-first downloads the include tree from `0:/sys` before parsing.
Modal `G90`/`G91` state carries in and out of a call the way RepRapFirmware's global state
does. `M400`, `M116` and `G4` are tolerated as explicitly non-motion; everything else
still fails closed, because an unrecognised line could be motion the replay would drop.
Recursion, depth and file-count are bounded.

The reader stayed fail-closed in the ways that matter: an unresolvable path, a missing
file or no resolver at all all refuse rather than parse a macro whose motion cannot be
seen.

## Tests

693 passing (62 new), 0 warnings.

- `MachineFrameTests` - the measured home pose both ways, involution, distance/radius
  invariance, no `-0`, arc-sense reversal, emitted words vs. Rhino previews, arc
  direction, the M208 box as a machine-frame fact, the reflected-joint identity the
  viewport poses with, and a full **Rhino -> G-code -> parser -> Rhino** round trip that

- `HomeMacroIncludeTests` - the board's real macros, copied into `fixtures/` as tracked
  provenance (`Robotics/` is git-ignored) exactly like `potterbot-config.g`. Covers both
  shapes the board has shipped (one `M98` plus an inline arm block, and full delegation
  where the trigger exists *only* inside a callee), the end-to-end verified-home replay
  that must yield a **known** arm mode, modal state across a call, and every fail-closed
  path.
- `RobotRobustnessTests` - the base transform is identical for every pose, while the
  rail swings with J1 and is untouched by J2, and the proximal arm does both.
- `GcodeTests` - the five assertions that pinned literal emitted coordinates now ask a
  helper for the emitted form of a Rhino position, so they read in design-frame terms.

### 4. The model is pinned

`robot.xml` has now been corrected against the physical machine four times, twice in this
release alone and twice in opposite directions. None of those regressions was visible to
the existing tests: the FK self-check cannot see which link a joint drives, because a
vertical lift commutes with a vertical-axis rotation and the nozzle lands in the same
place either way.

New `ShippedRobotModelTests` is a deliberate change-detector over the whole shipped
definition - joint chain (kind, parent, child, order), pivots, homes, firmware ranges,
link layers and lengths, reach annulus, calibrated home pose, arm mode, base placement,
and the registration being a pure translation, which is what makes the base rotation
readable off the viewport. Any edit to `robot.xml` fails it. Verified by mutating a
built copy: changing J1's parent and the base rotation trips three assertions.

It closes with the two properties the numbers exist to produce - the posing chain still
matching analytic FK, and the calibrated home pose solving to the joints `M114` actually
reported (-18.489 / -116.054) in the machine's own arm mode.

## Verification

**Motion and live tracking confirmed on the machine, 2026-08-26.** Jogging and the live
view move correctly under the frame map, which is what settles the reflection - two
right-handed Cartesian frames cannot be related by one, so the physical machine is
mirrored relative to the model (mirrored CAD export, or an inverted proximal-motor
direction). Worth establishing which, but it does not change the map.

**Base orientation confirmed** on the machine 2026-08-26 at the existing values; the
temporary `baseRot`/`baseOffX`/`baseOffY` inputs were removed again and the numbers live
in `robot.xml`.
