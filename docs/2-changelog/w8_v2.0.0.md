# Changelog - Week 8, 31-08-2026, V. 2.0.0

**Release Date**: Week 8, 31-08-2026
**Version**: 2.0.0 (previously 1.13.0)
**Object**: feat: robot-agnostic architecture - one Robot Definition, one Robot Simulation, slicer-only use

## Overview

Until 1.13.0 the plug-in *was* the lab's SCARA. Robot choice was not a thing you
selected; it was baked into component defaults, tooltips, the coordinate frame, the
placement warnings and two separate simulator components. Using the slicer on any other
machine meant reading the source to find out which parts were lying to you.

2.0.0 makes the robot an explicit selection carried on one wire. Generic slicing,
placement, extrusion, G-code and bead preview no longer know or care what is holding the
nozzle, and they now run with **no robot selected at all**.

The major version reflects the ribbon change, not a break in saved files: every shipped
component GUID is unchanged and existing definitions open and solve as before.

---

## 1. Robot Definition - one wire, not per-component hard-coding

**New component** `IAMLab Robot Definition` (**4 Robot**, GUID `a1a2…0025`). It emits a
stable string, `iamlab-robot:v1:<profile-id>`, which every robot-dependent component
accepts on a single `robot` input.

Shipped profiles:

| id | mechanism | program | direct control |
|---|---|---|---|
| `none` | None | RepRap G-code | - |
| `generic-cartesian` | Cartesian | RepRap G-code | - |
| `generic-duet-cartesian` | Cartesian | RepRap G-code | Duet |
| `potterbot-scara-v4` | SCARA | RepRap G-code | Duet |

`RobotCatalog.Resolve` accepts the wire format, canonical ids, and short aliases
(`"scara"`, `"none"`), so a plain panel string works as well as the component.
The format is versioned: an unknown definition raises a clear error instead of silently
resolving to the wrong machine - the failure mode that matters when the string selects
the kinematics that validate a print.

`RobotProfile` (`Core/Robot/RobotProfile.cs`) is immutable and Rhino-independent, and
carries selection plus machine defaults only - no preview meshes, no network session.
Rhino model loading stayed in the plugin project; Duet transport stayed in `Duet/`.

**Adding a robot** is one `RobotCatalog` entry, plus a solver in `Core/Robot/` only if it
needs IK, plus a mesh provider in `IAMLabSlicer/Robot/` only if it should be drawn. A
Cartesian machine needs neither. No reflection, no plugin framework, no new dependency.

## 2. One simulator instead of two

**New component** `IAMLab Robot Simulation` (**4 Robot**, GUID `a1a2…0026`) replaces the
separate per-machine simulator components. Its first input is the definition.

- `none` - no IK is attempted, `reachOK` reports true, and the component is a plain
  continuous G-code/toolpath and extrusion viewer
- `potterbot-scara-v4` - the existing `RobotChecks` / `ScaraKinematics` walk, the posed
  `Robot_Assembly.3dm`, the reach annulus and Cartesian envelope, unchanged

**The numerical solvers were not touched.** The unification is dispatch only.

The superseded per-machine simulator components are now `GH_Exposure.hidden`: off the
ribbon, still deserialized, still solving. Saved documents open unchanged.

The replacement deliberately took a **new** GUID rather than inheriting the SCARA
component's `d1a2…0004`. Its input list differs, and reusing a shipped GUID under a
changed socket layout silently remaps saved wires - the one failure this migration could
not afford.

## 3. Continuous extrusion preview - the scrub bug

**Reported**: scrubbing the simulation showed the print as many separate extrusion
instances rather than one continuous bead.

The cause was the preview cache's incremental path. On a forward scrub tick it built the
*delta* range as its own swept mesh - separately capped at both ends - and appended it to
the accumulated mesh. Every tick therefore welded a fresh pair of end caps into the
middle of what should have been one continuous bead, leaving disconnected topology at
every slider position.

The append path is gone. `ExtrusionPreview` now always builds the visible prefix as
maximal extrusion runs from the start of the job, via the new Rhino-free
`Core/Paths/ExtrusionHistory.VisibleRuns`. A continuous deposition path is one run at
every scrub position, forwards and backwards, and travel moves still break runs where
they should.

Extracting the run logic into Core is what makes it testable at all: `ExtrusionHistoryTests`
covers forward extension, travel gaps and backwards scrubbing without Rhino.

## 4. Separated concerns in the G-code path

- **Coordinate frame** is now data, not a constant. `GcodeConfig.CoordinateFrame`
  (`Identity` / `LegacyScara`) comes from the robot definition, applied in the four
  emitters and nowhere else; arc sense flips with the reflection. The active frame is
  reported in the component's `info` output (`frame:…`)
- **Extrusion quantity** moved out of the builder into `Core/Extrusion/RamExtrusion.cs`
  (`RamTravelPerPathMm`, `DepositedVolumeMm3`), so *how much material* is testable
  independently of *which dialect prints it*
- `IAMLab G-code` renamed `IAMLab G-code Generator`, description made material-neutral,
  GUID unchanged

**The Duet layer was not redesigned.** `DuetSession`, `DuetPollClient`, the command queue,
emergency stop, reply correlation, upload and file management are byte-for-byte unchanged,
and the fail-closed SCARA gates on upload and jog still apply to the shipped Potterbot
profile. An unsupported profile cannot weaken that gate because it cannot reach it.

## 5. Generic components made genuinely generic

- **Place** no longer emits a SCARA reach warning. Placement is robot-independent;
  Robot Simulation is the single reach validator, and the duplicate check disagreed with
  it for non-SCARA targets anyway
- Removed SCARA rationale from the G-code hop-speed and per-axis accel/jerk tooltips -
  those inputs are ordinary firmware limits
- **Slice** describes a "contour tree", not a "clay contour tree"
- `ExtrusionPreview` and `ToolpathSampler` no longer document themselves as belonging to
  "the previous per-machine simulators"

## Known limitations carried deliberately

### Direct Duet control is still SCARA-only

`generic-duet-cartesian` declares `ControlKind.Duet`, but **no component in 7 Print reads the
robot definition**. Those gates still validate against the shipped Potterbot limits.

This was a deliberate scope boundary: the SCARA gate is what refuses an upload that would
crash the arm, and making it profile-driven without equivalent regression tests could only
weaken it. So for a non-SCARA Duet machine, 2.0.0 delivers Duet/RRF *G-code generation*, not
direct control. The Robot Definition component emits a Remark saying exactly that whenever a
non-SCARA profile advertises Duet control, so the canvas does not imply otherwise.

Wiring the Duet components to the definition is the natural next increment; it needs its own
gate tests first.

### The unwired-frame default

`GcodeConfig.CoordinateFrame` defaults to `LegacyScara`, and an **unwired** `robot` input
on the G-code generator resolves to `potterbot-scara-v4`.

Every G-code emitted before 2.0.0 carried the calibrated Potterbot reflection about
`y = -x` (1.13.0). Defaulting to `Identity` would silently mirror the output of every
saved definition in the lab. A Cartesian user must therefore wire a definition to get the
identity frame their machine expects. The active frame is printed in `info` so the choice
is never invisible, but it remains a SCARA-shaped default in an otherwise robot-agnostic
path.
