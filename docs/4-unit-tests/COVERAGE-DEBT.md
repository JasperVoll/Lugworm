# Coverage debt

Deliberately untested paths, with why they are hard and how to close them.
Add a row rather than hiding code from coverage; never defer safety-critical behavior.

| Path | Why hard | Escape plan |
|---|---|---|
| Shipping-runtime coverage outside `tests/FrameworkSmoke` | The full suite still targets net10; the focused suite reuses culture, JSON, G-code, terminal, jog-repeat, poll and console-expiry assertions on net48/net7/net7-windows. | Add each newly touched pure policy to the linked suite. Do not imply that a green focused runtime run covers all Core or the Rhino plugin. |
| Historical GH definitions and functional saved values | The current-source contract/archive gate passes in Rhino, but it has no pre-3.0 fixture or solved saved RSM/goal/GraphMapper values. | Supply sanitized historical files and add targeted value/solve assertions. Current-source default/expanded wire round-trips are not evidence of every migration or cache-persistence behavior. |
| `Lugworm.Core/Duet/PrintLogSink.cs` — bounded-queue drop path (`RowsDropped` per file, `RowsDroppedTotal`, "queue full" error, reset on open) | Needs a consumer genuinely slower than the producer. The pump drains an unusable target instantly (the writer fails fast), and the public API exposes no seam to stall it, so any test that tries to fill the queue is a race. | Inject the writer factory (or an `Action` executed per command) so a test can block the pump deterministically, then assert drops. The property that actually protects the poll loop — the producer never blocks — is covered by `ProducerNeverBlocks_EvenWhenTheTargetIsUnusable`. |
| `Lugworm/Duet/MachineSession.cs` — print-log poll-loop wiring, owner registration, deferred-open triggers | The xUnit project references Core only; `MachineSession` lives in the plugin assembly, which needs Rhino/Grasshopper assemblies (`ExcludeAssets="runtime"`). | Stand up a plugin-layer test target, or extract the routing state machine into Core behind an interface. Covered meanwhile by the on-machine protocol in `docs/dev/TESTING.md` (1.10.0 rows). |
| `Lugworm/Components/DuetLiveViewComponent.cs` — log inputs/outputs, viewport trail, rising-edge export | Same plugin-assembly limitation; also requires a live Grasshopper canvas. | Same as above; manual protocol rows cover the observable behavior. |
| `Lugworm/Components/MachineComponentBase.cs` — the per-component `ActionGates()` overrides | Plugin assembly (needs Rhino/Grasshopper). Each override reads live session state together with component-specific conditions (a selected file, a validated job, a profile error) to decide which actions it names and when. | The gate set and the severity policy are Core since 4.4.0 - `Core/Machine/ActionGatePolicy.cs` over a plain `MachineActionState`, pinned by `ActionGatePolicyTests`; `ReportActionGates` is now only `AddRuntimeMessage`. What is left is each component's own gate list, covered by the 1.12.0 rows in `docs/dev/TESTING.md` (unhomed Print warns, then unsilences after a verified home). |
| `Lugworm/Components/DuetLiveViewComponent.cs` — `InverseRrf` branch selection from the session's tracked `ArmConfiguration` | Same plugin-assembly limitation; the input is live session state and the output is a posed viewport mesh. The IK itself is Core-tested (`HomedArmModeTests`), but the *choice* of preferred arm mode is not. | Same as above. The 1.12.0 protocol rows check the drawn elbow against `M114`, including the deliberate unhomed straight-arm render that must not be suppressed. |
| `Lugworm/Duet/MachineSession.cs` — machine-trust evaluation and the transaction-side refusal (`EvaluateTrust`, `TrustRefusalReason` inside `RunCommandAsync`/`RunGatedCommandAsync`, 2.6.0/AUD-SAF-004) | Plugin assembly (same Rhino/Grasshopper reference limitation). The trust RULE itself is Core-tested (`MachineFingerprintTests`), as is the client-side probe (`DuetClientTests`), but the session wiring — first-connection baseline, reconnect reprobe, refusal thrown inside the serialized transaction — is not. | Extract the trust state machine into Core behind a snapshot interface, or cover it in a future plugin-layer test target. Meanwhile the manual checklist carries a needs-hardware row: connect, expect first-connection baseline; simulate a fingerprint change, expect diagnostic-only + "Trust connected machine" recovery. |
| `Lugworm/Ui/BackgroundFileWork.cs` — stale-completion rejection, cancel-on-remove, single UI-thread completion (2.6.0/AUD-PERF-001) | The completion path runs through `RhinoApp.InvokeOnUiThread` and `ExpireSolution`, which need a live Rhino; the coordinator is small but its observable effect is a canvas re-solve. | Abstract the UI-thread marshal behind an injectable action to unit-test key/supersede/error-retention logic in isolation. Meanwhile the manual checklist covers slow-share load/save, document-close during a pending write, and last-good replay. |
| `Lugworm/Convert/DocUnits.cs` + per-component unit wiring (2.6.0/AUD-COR-001) | The adapter is exercised only through Rhino geometry types and viewport draws; Core deliberately never sees document units. | The manual checklist runs the slicer-only path in mm, inch and metre documents and compares physical print size and previews. A headless-Rhino test target (Rhino.Testing) is the eventual escape. |
| `Lugworm/Duet/LiveViewportController.cs` + `Robot/LiveRobotConduit.cs` (3.0.0) | The pump, the UI-thread ticks, the conduit draw and the Rhino redraw need a live Rhino; the pure parts (`LivePoseTimeline`, `LiveDisplayPolicy`, `LivePathDeviation`, `DeviationColorScale`) are Core-tested. | Manual rows LV1-LV5 (TESTING) and 7d (final round). An integration test against a temp directory could run the adapter through the coordinator's tests (same fixtures, real files) without Rhino - worth adding next. |
| `Lugworm/Ui/Console/` shell, `Pages/`, `ConsoleInteractionState`, `DuetConsoleForm` dialogs (3.0.0) | Skia drawing, WinForms dialogs, cursor/capture and timers; the gate (`PrintConsoleButtons`), the next action (`ConsoleNextAction`) and the state are Core-tested, and `tests/tooling/test_console_parity.py` pins the release paths in source. | Manual rows SH1-SH5, CP1-CP6, 7b. | `Lugworm/Ui/LegendRenderer.cs` and `Components/LegendComponent.cs` (4.0.0) | `LegendSpec`, `ColorSchemes` and `NiceTicks` are Core-tested, but the y-up layout frame, the viewport overlay, the plane-fixed mesh/text backend and the camera-facing billboard all run against Rhino display types. A drift between the three placements is exactly what the shared frame exists to prevent and exactly what no test checks. | A headless layout test over the pure frame (positions and label boxes in the y-up space, before any Rhino transform) would cover most of it. Meanwhile section 4 of the 4.0.0 round. |
| `Lugworm/Ui/SettingsIo.cs` and `SettingsRegistry.cs` (4.0.0) | `ComponentSettings` (schema, versioning, culture invariance) is Core-tested, and since 4.4.0 so is the classify-and-plan step. What is left in the plugin is the object half: creating or widening the slider / toggle / panel / value list, doing it under one undo event, and the document-scoped folder registration with its rescan-on-change. | The dangerous case - silently overwriting a user's upstream component - is now decided by `Core/Settings/SettingsPlan.cs` and pinned by `SettingsPlanTests` (create / update / skip with the reason, over a plain description of each input's sources); the capture side asks the same rule. For the rest, section 6 of the 4.0.0 round, especially 6.5 and 6.13. |
| `Lugworm/Duet/MachineSession.cs` - handing the glitch filter's FILTERED view to the position consumers (4.4.0) | Plugin assembly: the xUnit project references Core only. Core now pins that `AxisGlitchFilter` never writes into the snapshot it is given and that every `GlitchResolution` carries both views, but nothing checks the half that decides which view the program actually uses - that the poll loop and `FlushGlitchFilter` pass `released[r].Snapshot`, never `RawSnapshot`, to retention, diagnostics, the print log and `PollCompleted`, and that `_latest` keeps the reply as polled. A regression here is silent: every repair would simply vanish from the live view and the CSV while all Core tests stay green. | Same escape as the other `MachineSession` rows - lift the release-routing loop into a Core-testable type over the seam so a fake filter can prove which view each consumer sees. Meanwhile the 10a rows of the archived 4.0.0 test round are the only evidence. |
| `Lugworm.Core/Paths/Spiral.cs` - `NestedChain` on rings whose area centroid falls outside their own material (a deep crescent or C-section) (4.4.0) | The depth probe is the ring's area centroid. For an outline concave enough that the centroid lands in its own notch, the probe can sit outside the ring one step further out, the forest then reports two rings at one depth and the stack degrades to independent rings. That is the safe direction (a missed spiral, never a blend over air), but no test pins which outlines fall on which side, because "concave enough" depends on the offset distance as well as the shape. | Fall back to a probe guaranteed to lie on the ring (the vertex-nudged-toward-the-centroid point `Nesting` already uses privately) whenever the centroid is outside its own ring, then add a crescent fixture asserting one spiral. Until then treat spiral/Fermat infill on crescents as correct but conservative. |
